\chapter{Testing and Validation}
\label{chap:testing-and-validation}

This chapter documents the current testing and validation surface as it exists
in the repository now. It is based on the active root README, the local-agent
runbook, \texttt{docs/ai\_assistants/STATUS.md}, the validation ledger, the
current \texttt{CMakePresets.json}, and \texttt{source/tests/CMakeLists.txt}.
It records the observed baseline for the \texttt{WorkInProgress} branch at
commit \texttt{7097bc395d11b269692e62d39021cce220e0b1ad} on 2026-07-23.

This chapter does not treat a successful build as scientific validation. It
separates configure/build evidence, CTest inventory, focused sanitizer checks,
and scientific or numerical validation.

\noindent\textbf{Objective.} Describe the available test layers, the current
validation presets, the meaning of the recorded evidence, and the current
limits of the repository's validation surface.

\noindent\textbf{Audience.} Developers, maintainers, and reviewers who need to
judge the current quality bar for code, runtime, and documentation changes.

\noindent\textbf{Scope.} Cover Google Test, CTest, unit tests, smoke tests,
regression tests, integration checks, numerical tests, scientific validation,
ASan, UBSan, LSan, the focused leak path, the test presets, the expected
disabled tests, and how to interpret the observed results.

\noindent\textbf{Status.} Confirmed by source inspection and local command
execution on 2026-07-23. The chapter records the current validation surface
rather than a hypothetical future gate.

\section{Validation layers}
\label{sec:test-validation-layers}

The repository uses several validation layers, each with a different claim.
The layers should be read from bottom to top:
\begin{itemize}
\item configure and build confirm that the current preset and target graph are
still coherent for the selected scope;
\item unit and regression tests confirm narrow code contracts and selected
runtime invariants;
\item smoke tests confirm that small startup and execution paths still launch
and terminate cleanly;
\item focused sanitizer runs confirm a bounded ownership or lifetime path;
\item scientific validation requires explicit formulations, references,
fixtures, expected values, and independent review where appropriate.
\end{itemize}

The important boundary is that the layers do not imply each other. A green
build does not prove a green CTest run. A green CTest run does not prove
scientific correctness. A focused sanitizer does not prove repository-wide leak
freedom.

\section{Focused sanitizer path}
\label{sec:test-focused-sanitizer}

The repository does not expose a universal sanitizer preset. Instead, it has a
focused sanitizer-enabled executable in \texttt{source/tests/CMakeLists.txt}.
The current contract is:
\begin{itemize}
\item target: \texttt{genesys\_test\_simulator\_plugin\_completion\_lifetime};
\item compile options under GNU or Clang: \texttt{-fsanitize=address} and
\texttt{-fno-omit-frame-pointer};
\item link option: \texttt{-fsanitize=address};
\item runtime environment:
\texttt{ASAN\_OPTIONS=detect\_leaks=1:halt\_on\_error=1} and
\texttt{LSAN\_OPTIONS=exitcode=23}.
\end{itemize}

The purpose of this target is narrow: it exercises the temporary plugin-model
completion path and checks that the bounded ownership/lifetime slice exits
cleanly. It proves that the focused path is clean. It does not prove global
leak freedom, whole-repository UB freedom, or any broader scientific claim.

\section{Interpreting results}
\label{sec:test-result-interpretation}

The chapter should interpret results conservatively:
\begin{itemize}
\item configure success means the current preset graph is coherent;
\item build success means the affected targets compiled in the current tree;
\item CTest inventory means the current tree exposes the expected tests;
\item CTest execution means the registered tests actually passed in that run;
\item sanitizer success means the focused path did not trip the checked class
of memory or UB defect;
\item scientific validation requires domain-specific evidence, not just a
green build or a green smoke suite.
\end{itemize}

The most important negative rule is the one that prevents overclaim:
startup evidence is not functional correctness, and functional correctness is
not scientific validity.

\section{Practical reading rule}
\label{sec:test-practical-reading-rule}

When a developer reads this chapter, the safest interpretation is:
\begin{enumerate}
\item use the smallest preset that covers the change;
\item prefer focused regression tests over broad guesses;
\item use the focused sanitizer only for ownership and lifetime questions it
was designed to answer;
\item consult the status ledger when you need the last exact inventory or the
historical core baseline;
\item stop when the repository evidence and the chapter disagree.
\end{enumerate}

That rule keeps the chapter aligned with the repository's current evidence
discipline and prevents a validation story from drifting into assumption.
