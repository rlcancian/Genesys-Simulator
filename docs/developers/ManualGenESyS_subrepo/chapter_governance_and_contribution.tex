\chapter{Governance and Contribution}
\label{chap:governance-and-contribution}

This chapter is based on the current \texttt{WorkInProgress} branch.
The recorded baseline commit is \texttt{4571d5f45040b18ccd8746441f06cf4f08467c6d}.
It uses the active repository policy documents in
\texttt{README.md}, \texttt{docs/ai\_assistants/README.md},
\texttt{docs/ai\_assistants/GOVERNANCE.md},
\texttt{docs/ai\_assistants/STATUS.md}, and
\texttt{docs/ai\_assistants/ARCHITECTURE.md}.
It records the current contribution surface as it exists now, not a future
release policy.

\noindent\textbf{Objective.} Explain where GenESyS governance lives, how
contributors are expected to work, and which decisions remain reserved for a
human maintainer.

\noindent\textbf{Audience.} Contributors, maintainers, reviewers, and AI
assistants that need to align a change with the active repository policy.

\noindent\textbf{Scope.} Cover the canonical document hierarchy, branch and PR
conventions, autonomous-task boundaries, review expectations, validation
discipline, and the stop gates that require escalation instead of guesswork.

\noindent\textbf{Status.} Confirmed by source inspection on 2026-07-23. The
chapter documents the current governance and contribution surface rather than a
future idealized workflow.

\section{Where governance lives}
\label{sec:governance-where-it-lives}

GenESyS keeps policy in a small set of canonical files. The active authority
chain is:
\begin{itemize}
\item repository \texttt{/README.md} for the high-level repository baseline;
\item \texttt{docs/ai\_assistants/README.md} for the documentation entrypoint
  and routing rules;
\item \texttt{docs/ai\_assistants/GOVERNANCE.md} for normative AI-assisted
  development policy;
\item \texttt{docs/ai\_assistants/ARCHITECTURE.md} for durable technical
  boundaries;
\item \texttt{docs/ai\_assistants/STATUS.md} for the current operational state;
\item \texttt{docs/ai\_assistants/BACKLOG\_AUTONOMOUS.md} for work that may be
  executed autonomously;
\item \texttt{docs/ai\_assistants/BACKLOG\_HUMAN.md} for decisions that must
  not be guessed;
\item the applicable runbook under \texttt{docs/ai\_assistants/runbooks/}
  when execution details are needed.
\end{itemize}

The practical rule is simple: policy comes from the canonical documents, not
from older notes, historical PRs, or stale snapshots. If a task touches
architecture, ownership, public interfaces, security, persistence, plugins, or
scientific behavior, the architecture document must be read as part of the
current source of truth.

\section{Branch and review conventions}
\label{sec:governance-branch-review}

The active integration branch is \texttt{WorkInProgress}. Bounded feature work
uses dated branches of the form \texttt{WiPYYYYMM/<short-scope>}. A normal PR
targets \texttt{WorkInProgress} unless a maintainer explicitly selects another
base.

Current contribution policy also requires that PRs:
\begin{itemize}
\item stay small, bounded, and reviewable;
\item describe scope, non-goals, impact, validation, and remaining risks;
\item remain draft until the required evidence is reviewed;
\item avoid merge while mandatory validation is red, incomplete, or ambiguous;
\item use merge commits when repository tooling requires them;
\item delete the source branch after merge when the tooling supports it.
\end{itemize}

The repository currently treats the promotion flow as
\texttt{feature branches -> WorkInProgress -> YYYYs -> currentStable -> master}.
Ordinary development work does not target the stable promotion branches.

\section{How contributors are expected to work}
\label{sec:governance-contribution-flow}

The preferred contribution flow is conservative:
\begin{enumerate}
\item inspect the current source tree and the canonical policy files first;
\item identify the exact scope and avoid mixing unrelated concerns;
\item make the smallest change that satisfies the task;
\item preserve pre-existing user work unless the task explicitly says otherwise;
\item validate at the narrowest sufficient level before claiming success;
\item update the affected manual content when the change is material;
\item record the exact evidence used for the change;
\item open or update the PR with precise validation commands and results.
\end{enumerate}

For documentation work, the change is not finished until the affected manual
content has been reviewed and regenerated. For code, CMake, tests, packaging,
or workflow work, the change is not finished until the relevant source and
validation evidence both agree with the claimed behavior.

Autonomous work is narrower than general development. An autonomous agent may
execute only tasks explicitly marked as eligible in
\texttt{BACKLOG\_AUTONOMOUS.md}. It must not start a paused task, a
human-decision task, or a task whose scope is not executable from the current
repository state.

\section{Validation and evidence discipline}
\label{sec:governance-validation-evidence}

The contribution policy distinguishes source inspection, executed evidence, and
historical record. That distinction matters because a successful build or a
green test does not prove claims outside the exercised scope.

The minimum discipline for a material change is:
\begin{itemize}
\item confirm the current code or generated build graph before making factual
  claims;
\item run the narrowest relevant validation for the affected surface;
\item avoid presenting an unexecuted hypothesis as a supported feature;
\item keep scientific, numerical, security, and release claims separate from
  compilation success;
\item record the exact commit, branch, environment, and validation scope used
  for the claim.
\end{itemize}

Current governance also expects developers and reviewers to treat the manual as
a documented reflection of the repository, not as an independent source of
truth. If the manual and the current source disagree, the source wins.

\section{Human-decision boundaries}
\label{sec:governance-human-boundaries}

Some topics are intentionally reserved for explicit maintainer choice. The
human-decision backlog covers, among others:
\begin{itemize}
\item supported feature set and maturity declarations;
\item release scope and promotion decisions;
\item worker exposure beyond local or controlled-network deployment;
\item scientific reference packages and tolerances;
\item biological validity claims and benchmark selections;
\item future plugin ABI direction;
\item final publication and removal of draft status;
\item deletion of historical material before its retention gate.
\end{itemize}

An assistant must stop and escalate when a change depends on one of those
decisions. It should not pick a silent default for an item that the repository
has explicitly reserved for a maintainer.

\section{Contribution checklist}
\label{sec:governance-contribution-checklist}

Before considering a change ready, the contributor should be able to answer
all of the following:
\begin{itemize}
\item Which canonical policy files justify the change?
\item Which branch owns the work?
\item Which exact files changed?
\item Which evidence confirms the behavior or documentation claim?
\item Which limitations remain explicit?
\item Which items, if any, still require human decision?
\item Which downstream docs or status files must be updated?
\end{itemize}

If any answer is unknown, the change is not ready for promotion. If a decision
belongs to the human backlog, the correct outcome is escalation, not invention.

This chapter is intentionally conservative. It records the current governance
surface that contributors should follow today, and it keeps the boundary clear
between routine implementation work and decisions that require maintainer
approval.
