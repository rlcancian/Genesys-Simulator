\chapter{Worker Usage and Security}
\label{chap:worker-usage-and-security}

This chapter documents the current worker application as it exists in
\texttt{source/applications/worker/}, with supporting evidence from
\texttt{source/applications/mcp/} and the worker GUI wrapper in
\texttt{source/applications/gui/httpworker/}. The chapter is based on code
inspection of:

\noindent\textbf{Objective.} Explain how the worker is started, how clients
create sessions and use bearer tokens, how model and simulation requests are
scoped, how worker jobs behave, and why the current runtime must remain in a
trusted local or private-network boundary.

\noindent\textbf{Audience.} Operators, integrators, and developers who need to
use the worker directly or connect an automation client such as the MCP
connector.

\noindent\textbf{Scope.} Cover build and launch, public discovery endpoints,
session and token handling, model import and persistence, synchronous worker
jobs, transport limits, and the security boundary that currently applies.

\noindent\textbf{Status.} Confirmed by code inspection and aligned with the

\section{Build and launch}
\label{sec:worker-build-and-launch}

The worker target is named \texttt{genesys\_worker\_app}. The executable is
\texttt{genesys-worker}. The current build entry points are:
\begin{itemize}
\item \texttt{cmake --preset genesys\_worker\_app};
\item \texttt{cmake --build --preset genesys\_worker\_app --parallel "\$(nproc)"}.
\end{itemize}

The runtime entry point in \texttt{main.cpp} is intentionally thin. It creates
\texttt{BaseGenesysWebApplication} and forwards \texttt{argc/argv} to the
wrapper. The wrapper reads two command-line parameters:
\begin{itemize}
\item \texttt{--port <N>} selects the listening port;
\item \texttt{--max-requests <N>} stops the server after \texttt{N} requests.
\end{itemize}

The current default port is \texttt{8080}. A \texttt{--max-requests} value of
\texttt{0} means unlimited requests.

The worker can be started with:
\begin{verbatim}
./build/worker-debug/source/applications/worker/genesys-worker --port 8080
\end{verbatim}

For smoke testing, the bounded form is convenient:
\begin{verbatim}
./build/worker-debug/source/applications/worker/genesys-worker \
  --port 8080 --max-requests 1
\end{verbatim}

The current worker README documents the same target and executable names. The
MCP connector README expects the worker to be reachable through
\path{GENESYS_URL}, typically \path{http://localhost:8080} during local
development.

\section{Endpoint surface}
\label{sec:worker-endpoints}

The current router in \texttt{ApiRouter.cpp} exposes a conservative endpoint
surface:
\begin{itemize}
\item \texttt{GET /health};
\item \texttt{GET /api/v1/worker/info};
\item \texttt{GET /api/v1/worker/capabilities};
\item \texttt{POST /api/v1/auth/session};
\item \texttt{GET /api/v1/simulator/info};
\item \texttt{POST /api/v1/models};
\item \texttt{GET /api/v1/models/current};
\item \texttt{POST /api/v1/models/save};
\item \texttt{POST /api/v1/models/load};
\item \texttt{GET /api/v1/simulation/status};
\item \texttt{POST /api/v1/simulation/config};
\item \texttt{POST /api/v1/simulation/run};
\item \texttt{POST /api/v1/simulation/step};
\item \texttt{GET /api/v1/worker/jobs/\{jobId\}};
\item \texttt{POST /api/v1/worker/jobs/\{jobId\}/run};
\item \texttt{GET /api/v1/worker/jobs/\{jobId\}/result};
\item \texttt{POST /api/v1/worker/models/import-language}.
\end{itemize}

Only \texttt{/health}, \texttt{/api/v1/worker/info}, and
\texttt{/api/v1/worker/capabilities} are public discovery endpoints. The
remaining operations require \texttt{Authorization: Bearer <token>} and are
session-scoped.

The worker capability payload is useful because it makes the current staged
contract explicit. The implementation currently advertises:
\begin{itemize}
\item session API support;
\item session-scoped simulator ownership;
\item model creation and persistence;
\item simulation status, configuration, synchronous run, and synchronous step;
\item distributed-job discovery and polling flags;
\item model import support;
\item terminal job-result retrieval support.
\end{itemize}

At the same time, the capability payload also marks
\texttt{supportsBackgroundExecution = false} and
\texttt{supportsStreamingEvents = false}. That is the practical boundary: the
worker currently executes jobs synchronously and does not provide streaming
progress updates.

\section{Sessions and model scope}
\label{sec:worker-sessions}

The session manager creates one \texttt{Simulator} per session and stores each
session under a workspace directory rooted at the system temporary directory.
The workspace root is:
\begin{verbatim}
std::filesystem::temp_directory_path() / "genesys_worker_sessions"
\end{verbatim}

Each session gets a generated identifier with the \texttt{sess\_} prefix and a
generated opaque access token. The token service creates random hexadecimal
strings. The current implementation uses:
\begin{itemize}
\item a session identifier built from 12 random bytes;
\item an access token built from 24 random bytes.
\end{itemize}

The token is opaque and random. It is enough to gate the current session API,
but it is not production-grade authentication.

The session API allows clients to:
\begin{itemize}
\item inspect simulator metadata;
\item create a new model;
\item inspect the current model;
\item save and load a model inside the session workspace;
\item read simulation status;
\item configure and execute a simulation.
\end{itemize}

Model persistence is deliberately constrained to the session workspace. The
worker accepts only a filename basename through the save/load routes. The
service rejects paths that contain separators, parent-directory traversal, or
characters outside \path{[A-Za-z0-9._-]}.

The model-import route is plain-text only. It accepts the current GenESyS model
language specification as request body text and rejects blank or invalid
specifications.

\section{Worker jobs}
\label{sec:worker-jobs}

Worker jobs are a separate in-memory abstraction layered on top of the session
API. They are currently created from the active model in the owning session and
stored with a monotonic identifier of the form \texttt{job-N}.

The job lifecycle is:
\begin{itemize}
\item \textit{Queued} when the job is created;
\item \textit{Running} while the synchronous execution is in progress;
\item \textit{Finished} after a successful run;
\item \textit{Failed} if snapshot loading or simulation execution fails.
\end{itemize}

When a job is created, the worker persists a snapshot file in the session
workspace with the pattern \texttt{job\_\{jobId\}.gen}. That snapshot decouples
future execution from later model edits in the live session.

The worker also stores a creation marker of the form \texttt{seq-N}. That
marker is a stable ordering aid, not a public schedule guarantee.

Job access is session-bound:
\begin{itemize}
\item \texttt{GET /api/v1/worker/jobs/\{jobId\}} returns job metadata only when
the calling token owns that job;
\item \texttt{POST /api/v1/worker/jobs/\{jobId\}/run} loads the stored
snapshot and runs the job synchronously;
\item \texttt{GET /api/v1/worker/jobs/\{jobId\}/result} is available only after
the job has a terminal result;
\item jobs from another session return access-denied errors.
\end{itemize}

If a client asks for the terminal result too early, the worker returns a
\texttt{ResultNotReady} condition. That is intentional: the result endpoint is
terminal-state only.

The synchronous run path updates the in-memory job state, loads the saved
snapshot, starts the simulation inline, and then stores a minimal terminal
summary. The stored result includes simulated time, replication counters,
replication length, warm-up period, and the paused flag when available.

\section{Transport and security limits}
\label{sec:worker-transport-security}

The transport layer is intentionally simple:
\begin{itemize}
\item one request per connection;
\item no keep-alive;
\item no chunked-transfer decoding;
\item no TLS;
\item bounded request reads;
\item fixed socket timeouts.
\end{itemize}

The server binds with \texttt{INADDR\_ANY}, so it listens on all interfaces
available to the host. That means the code itself does \emph{not} enforce a
loopback-only policy. The intended operational boundary is therefore a local or
trusted private network protected by external controls, not a public Internet
deployment.

The current transport guardrails are:
\begin{itemize}
\item request size limit: 1 MiB;
\item socket receive timeout: 5 seconds;
\item socket send timeout: 5 seconds;
\item \texttt{413 Payload Too Large} for oversized requests;
\item \texttt{408 Request Timeout} when a request is not completed in time.
\end{itemize}

The router also returns ordinary HTTP error codes for the usual failure
conditions:
\begin{itemize}
\item \texttt{401} for missing or invalid bearer tokens;
\item \texttt{404} for unknown routes;
\item \texttt{405} for unsupported methods;
\item \texttt{409} for operations that require a current model;
\item \texttt{400} for malformed payloads;
\item \texttt{500} for unexpected runtime failures.
\end{itemize}

The worker README is explicit that the current session token is provisional and
not production-grade authentication. The same README also states that public
Internet exposure is not approved. The manual should preserve that boundary.

\section{Recommended local workflow}
\label{sec:worker-local-workflow}

A conservative local workflow is:
\begin{enumerate}
\item start \texttt{genesys-worker} on \texttt{localhost} or inside a trusted
private network;
\item call \texttt{GET /health} to confirm the process answers;
\item call \texttt{POST /api/v1/auth/session} and keep the returned token;
\item call \texttt{GET /api/v1/worker/info} or
\texttt{GET /api/v1/worker/capabilities} to confirm the worker flavor;
\item create or import a model;
\item save or load the model only inside the session workspace;
\item configure and run the simulation;
\item create a worker job only after the current model is ready;
\item run the job synchronously and retrieve the terminal result after it
finishes.
\end{enumerate}

An example local sequence is:
\begin{verbatim}
curl http://localhost:8080/health
curl -X POST http://localhost:8080/api/v1/auth/session
curl -H "Authorization: Bearer <token>" \
  http://localhost:8080/api/v1/worker/info
curl -H "Authorization: Bearer <token>" -X POST \
  http://localhost:8080/api/v1/models
\end{verbatim}

For the MCP connector, the worker address is supplied through
\texttt{GENESYS\_URL}. The connector README assumes that a session token is
created once per conversation and then reused by subsequent tool calls.

\section{Troubleshooting and current limitations}
\label{sec:worker-troubleshooting}

The current implementation is still staged and conservative. The most useful
operator-facing constraints are:
\begin{itemize}
\item there is no TLS;
\item there is no production-grade authentication;
\item there is no background job executor;
\item there is no streaming job progress feed;
\item worker jobs remain session-scoped;
\item model save/load is restricted to safe filenames in the session workspace;
\item the server does not guarantee loopback-only binding.
\end{itemize}

If a request fails, the first things to check are:
\begin{itemize}
\item the worker is actually listening on the expected port;
\item the bearer token came from \texttt{/api/v1/auth/session};
\item the token still belongs to the same session as the job or model;
\item the request body is plain text for model import and JSON-with-filename
for save/load;
\item the model exists before configuring or running simulation;
\item the job belongs to the same session before polling or running it.
\end{itemize}

Common failure signatures are:
\begin{itemize}
\item \texttt{401 UNAUTHORIZED}: missing, malformed, or expired token;
\item \texttt{400 BAD\_REQUEST}: invalid request body or malformed payload;
\item \texttt{409 NO\_CURRENT\_MODEL}: no active model exists yet;
\item \texttt{413 PAYLOAD\_TOO\_LARGE}: transport limit exceeded;
\item \texttt{408 REQUEST\_TIMEOUT}: the request did not arrive in time;
\item \texttt{404 NOT\_FOUND}: route mismatch;
\item \texttt{405 METHOD\_NOT\_ALLOWED}: wrong HTTP method.
\end{itemize}

The chapter deliberately does not promise public deployment readiness. The
current worker is a controlled application service for local or private use
until the security backlog items are completed and validated.
