\chapter{Model Representation and Persistence}
\label{chap:model-representation-and-persistence}

This chapter explains how a GenESyS model exists in memory, how the kernel
serializes that state, and how the current load/save path rebuilds the object
graph through the plugin-based persistence layer. It is the bridge between the
model structure already described in the previous chapters and the on-disk
artifacts that users and developers actually inspect.

\noindent\textbf{Objective.} Explain how models are represented internally and
persisted to disk.

\noindent\textbf{Audience.} Developers who need to inspect model files,
understand loading behavior, or reason about save and reload semantics.

\noindent\textbf{Scope.} Cover the runtime object graph, the current
\texttt{.gen} persistence path, the load and save pipelines, ownership during
round-trip, and the practical limits of the implementation.

\noindent\textbf{Status.} Confirmed by code inspection and supporting unit
tests. The chapter follows the current \texttt{Model}, \texttt{Persistence\_if},
\texttt{PersistenceRecord}, \texttt{GenSerializer}, and
\texttt{PersistenceDefaultImpl2} implementations, plus the round-trip tests
already present in the repository.

\section{What is represented in memory}
\label{sec:model-persistence-memory-structure}

The persistence story begins with the model object itself. A \texttt{Model}
owns the simulation-facing managers and the runtime services that must be
reconstructed when a model is opened again. In the current implementation that
includes the data manager, component manager, simulation controller, parser,
checker, persistence service, event manager, trace manager reference, and the
future-event list.

The important point is that persistence does not save a loose bag of objects.
It saves a model with ownership boundaries:
\begin{itemize}
\item \texttt{ModelDataManager} groups data definitions by runtime typename.
\item \texttt{ModelComponentManager} keeps the component set ordered by ID.
\item \texttt{ModelDataDefinition} carries the metadata and the internal or
      attached data relations used by specialized objects.
\item \texttt{ModelComponent} extends that same base infrastructure for flow
      behavior.
\item \texttt{ModelSimulation} and \texttt{ModelInfo} hold simulation settings
      and model metadata.
\end{itemize}

This is why the persistence code always serializes the same core categories:
simulator information, model metadata, simulation parameters, model data
definitions, and components. It is also why a model reload must re-establish
the object graph instead of just filling a text buffer.

\section{How saving works}
\label{sec:model-persistence-saving}

The public entry point for saving is \texttt{Model::save(std::string)}. That
method delegates to the configured persistence service and only adds a trace
message around the result. The real formatting and file writing happen inside
\texttt{PersistenceDefaultImpl2::save}.

The save pipeline is straightforward but important:
\begin{itemize}
\item the persistence service selects a serializer from the filename
      extension;
\item \texttt{.xml} uses \texttt{XmlSerializer};
\item \texttt{.json} uses \texttt{JsonSerializer};
\item \texttt{.cpp} uses \texttt{CppSerializer};
\item every other extension falls back to \texttt{GenSerializer}.
\end{itemize}

For the \texttt{.gen} path, the serializer then gathers the model in a fixed
order. It writes simulator information, model metadata, and simulation
parameters first. After that it writes model data definitions and model
components. The current implementation also skips internal statistical helper
objects such as \texttt{Counter} and \texttt{StatisticsCollector}, because they
are runtime support artifacts rather than user-authored model content.

The save code serializes only top-level components at level zero. That keeps the
saved graph focused on the actual model structure instead of duplicating nested
runtime helpers that are recreated by the owning objects themselves.

\section{How loading works}
\label{sec:model-persistence-loading}

Loading starts in \texttt{Model::load(std::string)}. Before the file is parsed,
the model is cleared so that stale runtime state does not survive the reload.
That clear step matters: it destroys pending events, transient entities,
components, remaining data definitions, and then resets all IDs.

The actual parsing logic lives in \texttt{PersistenceDefaultImpl2::load}. The
same extension-based dispatch is used here, except that \texttt{.cpp} is not
loadable. The loader accepts XML, JSON, and the default GenESyS text format.
If the file cannot be opened or parsed, the method returns \texttt{false} and
traces an error.

The load sequence has three distinct phases:
\begin{enumerate}
\item Parse the file into a serializer-specific in-memory store.
\item Instantiate the loaded objects through the plugin registry.
\item Reconnect the top-level component graph once all components exist.
\end{enumerate}

During instantiation the loader handles the core headers specially. It checks
the simulator version in the saved metadata, loads \texttt{ModelInfo} and
\texttt{ModelSimulation}, and then dispatches each remaining entry by
\texttt{typename}. If the typename cannot be resolved to a plugin, loading
fails. If a component is loaded successfully, its raw field record is kept so
the final connection pass can resolve the saved \texttt{nextId} and port data.

\section{The \texttt{.gen} layout}
\label{sec:model-persistence-gen-layout}

The default textual format is handled by \texttt{GenSerializer}. Its output is
deliberately simple and line oriented. The file begins with comment headers,
then writes simulator and model metadata, then writes data definitions, and
finally writes model components.

Each serialized line is produced from a \texttt{PersistenceRecord}. That record
behaves like a small associative table of fields and is the common container
passed through the \texttt{\_saveInstance()} and \texttt{\_loadInstance()} hooks.
The serializer linearizes the record by printing the numeric ID, the type name,
the quoted object name, and the remaining attributes as key-value pairs.
Textual values are quoted; numeric values are emitted without quotes.

The loader reverses that process with a conservative tokenization strategy. It
first protects quoted strings with placeholders, splits the line, reconstructs
key-value pairs, and then hands the resulting field table back to the plugin
loader. The code is intentionally pragmatic rather than fancy: it is a
compatible text format, not a general-purpose grammar tutorial.

The most important ordering rule is that entries are iterated by ID, not by the
order they happened to be inserted. That keeps the file stable enough to read
and diff while still letting the registries keep their own internal order.

\section{Ownership during round-trip}
\label{sec:model-persistence-ownership}

The persistence layer does more than store fields. It must preserve ownership
and reconstruction boundaries.

For data definitions, the base class \texttt{ModelDataDefinition} is
responsible for serializing its own core metadata. Its \texttt{\_saveInstance()}
method writes \texttt{typename}, \texttt{id}, \texttt{name}, \texttt{label},
and \texttt{reportStatistics}. Its \texttt{\_loadInstance()} method requires a
positive ID before it accepts the record back. Specialized subclasses extend
those fields with their own state.

For components, the load path depends on the plugin registry. A component is
created, inserted into the model, and then later reconnected using the saved
component fields. That two-pass reconstruction is necessary because component
connections can only be resolved once every referenced target already exists in
the component manager.

The manager layer also matters here. \texttt{ModelDataManager::insert()} makes
internal data materialize immediately after insertion, which keeps the runtime
state consistent for GUI flows and validation. \texttt{ModelComponentManager}
keeps components searchable by name and ID, and the loader uses that registry
when it reconnects the graph.

This is the point where \texttt{Model::clear()} becomes part of persistence,
even though it is not a serializer. Without the reset, a reload would mix new
objects with old runtime objects and the ownership graph would no longer be
trustworthy.

\section{Validation evidence}
\label{sec:model-persistence-validation}

The repository already contains tests that support this chapter.
\begin{itemize}
\item \texttt{test\_support\_persistence.cpp} exercises
      \texttt{PersistenceRecord} insertion, clearing, cloning, range insertion,
      and the numeric and string load/save helpers.
\item \texttt{test\_simulator\_runtime.cpp} contains multiple save/load
      round-trip tests for concrete model elements, including examples such as
      \texttt{CreateSaveLoadRoundTripPreservesBasicConfiguration},
      \texttt{ProcessPersistenceRoundTripPreservesConfigurationAndReconcilesInternals},
      \texttt{WritePersistenceRoundTripPreservesAllTextElementsInOrder}, and
      \texttt{LabelSaveAndLoadRoundTripPreservesLabelAndEnteringComponentName}.
\item The same runtime test file also exercises serializer output and confirms
      that the save path uses the current API and property names.
\end{itemize}

Those tests do not turn this chapter into a formal specification. They do,
however, establish that the current persistence code is not speculative text:
the round-trip behavior is already exercised in the tree.

\section{What this chapter does not claim}
\label{sec:model-persistence-limits}

This chapter stays within the current code base and does not generalize beyond
it. It does not promise a stable public file format ABI, because the code does
not document one. It does not claim that every old or future \texttt{.gen}
variant will remain loadable forever. It also does not describe the \texttt{.cpp}
serializer as a loadable format, because the current loader explicitly refuses
it.

The safest reading is practical: the model can be saved, the supported file
types can be loaded, the core object graph is rebuilt through the plugin
system, and the implementation already exposes the expected failure modes for
unknown typenames, unresolved component targets, and invalid input files.

\section{Final considerations}
\label{sec:model-persistence-final-considerations}

This chapter closes the gap between the abstract model structure and the
concrete file that leaves the application. For day-to-day work, the important
facts are simple:
\begin{itemize}
\item saving is a controlled traversal of the live model;
\item loading begins with a clean model state;
\item the \texttt{.gen} file is a linearized snapshot ordered by ID;
\item plugin dispatch reconstructs concrete data definitions and components;
\item component connections are restored only after all targets exist.
\end{itemize}

That is enough to reason about persistence bugs, round-trip behavior, and file
compatibility without guessing how the kernel behaves.

The next chapter moves from persistence to component-level data definitions,
which is where specialized objects and their supporting data become more
visible.
