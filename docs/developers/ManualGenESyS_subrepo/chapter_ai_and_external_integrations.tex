\chapter{AI and External Integrations}
\label{chap:ai-and-external-integrations}

This chapter documents the current AI and external-integration boundary as it exists in the active branch on 2026-07-23. It is based on the current tool libraries, GUI sources, model-specific example sources, CMake targets, and the repository guidance that classifies AI, external code, and process execution as explicit boundaries. The chapter describes the current snapshot, not a future idealized integration platform.

\noindent\textbf{Objective.} Explain how the current AI assistant stack is configured, how it sends provider requests, how audit and secret handling work, and how the current external code and process integrations are wired.

\noindent\textbf{Audience.} Developers and maintainers who need a faithful map of the current AI and external-integration boundary before changing providers, permissions, secret handling, model-specific AI flows, or runtime execution hooks.

\noindent\textbf{Scope.} Cover the AI assistant backend in \texttt{source/tools/AIAssistant}, the graphical AI Assistant application, the model-specific AI example, the current permission model, the audit and keyring flows, and the currently implemented external code/process integrations. Keep the discussion limited to the code tree that is actually present in the repository.

\noindent\textbf{Status.} Confirmed by repository inspection on 2026-07-23. The chapter is conservative about maturity: the AI assistant can talk to providers, keep an audit log, and drive model construction in controlled mode, but that does not imply public deployment readiness or scientific validation of the resulting workflows.

\section{Current AI boundary}
\label{sec:ai-boundary}

The current AI stack is split into three visible layers:
\begin{itemize}
\item \texttt{genesys\_tools}, which links the assistant backend with the rest of the simulator support libraries;
\item \texttt{genesys\_ai\_provider}, which contains the provider clients and the conversation service used to talk to OpenAI-compatible or Anthropic-style APIs;
\item \texttt{genesys\_ai\_assistant\_gui\_application}, which exposes the GUI front end for manual configuration, prompt entry, execution, and audit review.
\end{itemize}

At the model level, the AI-specific component path is implemented by \texttt{AISupport} and \texttt{AIAssistant}. The example application \texttt{StartAIAssistant} wires those classes into a runnable model-specific flow and is a useful concrete reference for how the AI boundary is consumed from a simulation model.

\section{Configuration and permissions}
\label{sec:ai-configuration}

The assistant configuration is intentionally deny-by-default. The public configuration structure exposes these controls:
\begin{itemize}
\item provider selection: \texttt{OpenAI}, \texttt{Anthropic}, \texttt{Local}, or \texttt{CustomHttp};
\item model identifier;
\item base URL;
\item API key environment-variable name;
\item temperature, timeout, and token budget;
\item network access permission;
\item model-mutation permission;
\item simulation-execution permission;
\item filesystem-write permission;
\item sandbox mode;
\item dry-run mode.
\end{itemize}

The lower-level conversation service currently supports \texttt{OpenAI}, \texttt{Anthropic}, and \texttt{Local}. The higher-level assistant facade also accepts \texttt{CustomHttp} and maps it to the OpenAI-compatible local client with a custom base URL. That distinction matters because it shows which option is a direct provider implementation and which option is a facade-level compatibility choice.

The readiness check in \texttt{AIAssistantDefaultImpl} requires a configured provider, a non-empty model name, a key when the selected provider requires one, and a base URL when the provider is \texttt{CustomHttp}. It also makes clear that model construction and simulation still require the explicit \texttt{allowModelMutation} and \texttt{allowSimulationExecution} gates.

\section{Provider pipeline}
\label{sec:ai-pipeline}

The provider pipeline is split into a provider-neutral request layer and provider-specific HTTP clients.

\texttt{AIConversationService} builds \texttt{ChatMessage} sequences from the system instructions, the conversation history, and the current user prompt. It owns the selected provider client, optionally loads a key from the configured environment variable, and then sends a synchronous chat-completion request with the configured model, temperature, token budget, and reasoning hint.

The transport layer in \texttt{HttpProviderClientBase} shells out to \texttt{curl}. The request body is written to a temporary file, the API key is written to a separate 0600 curl-config file, and both files are unlinked right after the request begins. That keeps the key out of the command line and out of shell history. The concrete clients then map the raw response body back to the provider-neutral response structure.

The current provider specializations are:
\begin{itemize}
\item \texttt{OpenAIProviderClientImpl}: OpenAI chat completions, optional organization and project headers, and reasoning-mode support through \texttt{highReasoningMode};
\item \texttt{AnthropicProviderClientImpl}: Anthropic Messages API with the top-level system field, the required version header, and the extended-thinking budget;
\item \texttt{LocalProviderClientImpl}: OpenAI-compatible local servers such as Ollama, LM Studio, or llama.cpp, with no key required unless the local server explicitly wants one.
\end{itemize}

The assistant facade adds one more compatibility path: \texttt{CustomHttp} is implemented through the local OpenAI-compatible client with a custom base URL. That keeps the current code aligned with existing OpenAI-style endpoints without inventing a separate transport stack.

\section{Audit and secret handling}
\label{sec:ai-audit-and-secrets}

The current audit trail is append-only and local. \texttt{AIAuditLog} writes JSON Lines under the XDG data directory, typically \texttt{\textasciitilde/.local/share/genesys/ai\_audit.log}, and can export the same records to CSV. Each entry stores the operation name, provider, model, prompt preview, success flag, dry-run flag, duration, and a capped error summary. It does not store API keys.

\texttt{AISecretStore} is the current OS keyring helper. On Linux it uses \texttt{secret-tool} when available, which means the GUI can save, load, and clear a key in the session keyring. If the helper is unavailable, the code falls back to an environment variable or a key typed into memory. The keyring helper shells out carefully, but it is still a host-level integration, not an in-process secret vault.

The GUI reflects that design. The AI Assistant window has dedicated controls to apply configuration, save and load a keyring entry, refresh the audit table, and export the log. It also shows the masked key only. The audit table is a read-only view of recent log entries loaded from the same local audit file.

\section{Sandbox and workflow control}
\label{sec:ai-sandbox-workflow}

The backend workflow is intentionally staged.

\texttt{analyzePrompt()} performs a provider call that summarizes the scenario and extracts the current GenESyS vocabulary. \texttt{createModelPlan()} performs a second provider call that returns a structured Markdown plan. \texttt{buildModel()} asks for a \texttt{.gen} model, writes it to a temporary file, loads it through \texttt{SimulatorFacade::loadModel()}, and deletes the temporary file afterwards. \texttt{configureSimulation()} can use the provider to extract simulation parameters from the experiment description, then applies the values to the current model. \texttt{runSimulation()} calls \texttt{simStart()} synchronously. \texttt{collectResults()} renders current simulation responses.

Two flags change the shape of that workflow:
\begin{itemize}
\item \texttt{sandboxEnabled} clears the current model before \texttt{buildModel()} starts, so the generated model begins from an empty canvas;
\item \texttt{dryRun} converts the mutating steps into previews, so the code reports what it would do instead of changing the model or starting the simulation.
\end{itemize}

The GUI exposes both flags. It also exposes a filesystem-write checkbox, but the inspected backend gates are centered on network access, model mutation, simulation execution, readiness, and provider availability. I did not confirm a dedicated backend enforcement path for filesystem writes in the current execution flow.

\section{GUI and model-specific example}
\label{sec:ai-gui-model-specific}

The AI Assistant GUI is a Qt6 application with four tabs: configuration, prompt and plan, execution and results, and audit log. The configuration tab pushes settings into \texttt{AIAssistantDefaultImpl}, optionally loads an API key from the keyring or an environment variable, creates the provider client, and refreshes the knowledge base from the simulator facade. The prompt tab collects the model description, experiment description, and freeform prompt. The execution tab drives the individual workflow steps or the full pipeline. The audit tab shows the local JSONL log and can export it as CSV.

The model-specific example \texttt{StartAIAssistant} shows a concrete in-model use case. It creates a \texttt{Simulator}, auto-loads plugins, constructs an order-routing flow, configures \texttt{AISupport} from environment variables, attaches an \texttt{AIAssistant} component, sets action mappings for the JSON response, and then runs a short simulation. The example is valuable because it shows the assistant not as a standalone chatbot, but as a model component that controls routing inside the simulation graph.

The current \texttt{AIAssistant} component expects an attached \texttt{AISupport} definition, renders a prompt with expression placeholders inside braces, asks the support service for a synchronous response, parses JSON fields such as \texttt{action}, \texttt{confidence}, \texttt{explanation}, and \texttt{values}, and then forwards the entity through the selected output port. If the response cannot be parsed, or if the action does not match the action mapping, the component routes the entity to the error output port.

\section{External code and process integration}
\label{sec:external-code-process-integration}

The external-integration path is broader than the AI assistant itself.

\texttt{CppForG} is a model component that compiles user-supplied C++ hooks, loads them as a shared library, and dispatches replication and entity callbacks through function pointers. Its companion \texttt{CppCompiler} can compile to an executable, a dynamic library, or a static library, and it can load and unload the resulting shared object.

\texttt{PythonForG} is the Python hook component. It stores hook code in the model, uses \texttt{PythonRuntime} to validate and execute the hooks, and can optionally forward an entity on error. The Python runtime is compile-time gated through \texttt{GENESYS\_HAS\_PYTHON\_INTEGRATION}, which means the source can exist even when the interpreter embedding support is not available in a particular build.

\texttt{RSimulator} and \texttt{RSimulatorRunner} are the R-side integration pair. The runner writes a temporary script, invokes \texttt{Rscript}, and stores last-run status, exit code, stdout, stderr, response payload, and file paths. The component wraps that runner inside a model component so that the simulation graph can call external R code as part of the flow.

These integrations share the same basic design constraints: keep the model ownership separate from the external runtime, bound execution, keep secrets out of logs and argv, and treat the host toolchain or interpreter as an integration dependency rather than as an implicit simulator feature.

\section{Current limitations}
\label{sec:ai-limitations}

The current code does not justify stronger claims than the ones above.
\begin{itemize}
\item The assistant can call providers, but provider access still depends on explicit permissions and a reachable endpoint.
\item The audit log is local and append-only; it is not a distributed observability system.
\item The keyring helper is optional and host-dependent.
\item The GUI exposes a filesystem-write permission control, but I did not confirm a dedicated backend enforcement branch in the inspected execution path.
\item \texttt{MCP} is not covered here because I did not confirm a current implemented runtime contract in the inspected AI integration path.
\item The Python integration remains experimental and compile-time dependent.
\item External execution hooks are integration boundaries, not proof of scientific correctness or general deployment safety.
\end{itemize}

The practical rule for this chapter is simple: document the implemented boundary, name the explicit permissions, and do not turn a functioning integration path into a maturity claim that the current code does not support.
