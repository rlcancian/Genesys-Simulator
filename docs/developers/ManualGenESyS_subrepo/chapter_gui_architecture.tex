\chapter{GUI Architecture}
\label{chap:gui-architecture}

This chapter documents the current Qt6 GUI architecture as it exists in the active branch on 2026-07-23. It is based on the current GUI sources, the generated UI file, and the extracted controller/service classes used by the \texttt{MainWindow} compatibility facade. The chapter describes the current snapshot, not a future idealized split.

\noindent\textbf{Objective.} Explain how the main graphical interface is composed, which classes own each responsibility, and how user actions travel from widgets to controllers, scene objects, and simulator callbacks.

\noindent\textbf{Audience.} Developers who need a faithful map of the GUI before changing actions, view wiring, property editing, plugin presentation, persistence, or simulation interactions.

\noindent\textbf{Scope.} Cover the MainWindow composition root, the widget and scene boundaries, controller and service responsibilities, signal/slot and callback wiring, model open/save flows, and the simulation action path.

\noindent\textbf{Status.} Confirmed by repository inspection on 2026-07-23. The chapter describes the current architecture snapshot and explicitly includes the remaining compatibility wrappers.

\section{MainWindow as the composition root}
\label{sec:gui-architecture-mainwindow}

\texttt{MainWindow} is still the GUI composition root. The current implementation is split across \texttt{mainwindow.cpp}, \texttt{mainwindow\_controller.cpp}, \texttt{mainwindow\_scene.cpp}, and \texttt{mainwindow\_simulator.cpp}, but the class itself remains the top-level place where UI objects are created, controller dependencies are wired, and compatibility slots are exposed.

The constructor in \texttt{mainwindow.cpp} creates the generated UI, the simulator, the trace and property support objects, the extracted controllers, and the helper services used by the editor. The generated \texttt{mainwindow.ui} file still provides the widgets, menus, tabs, toolbars, dock panes, and action objects, while the C++ constructor wires them into the controller stack.

The current design is not a pure passive view. \texttt{MainWindow} still owns some coordination duties:
\begin{itemize}
\item it creates the controller graph;
\item it registers the remaining compatibility slots used by the generated UI;
\item it connects scene signals to legacy handlers;
\item it keeps some cross-cutting state such as the active model tabs, selection state, and recent-file menu;
\item it mediates between the generated UI and the extracted controllers.
\end{itemize}

This means the GUI is already partially modular, but not fully flattened into independent presenter or service layers. The chapter therefore treats \texttt{MainWindow} as a compatibility facade that delegates selected responsibilities instead of pretending that the split is already complete.

\section{Controller and service map}
\label{sec:gui-architecture-controller-map}

The GUI is already organized around focused controller and service classes. Their current roles are visible in the class headers and in the constructor wiring inside \texttt{mainwindow.cpp}:
\begin{itemize}
\item \texttt{ModelLifecycleController} owns new/open/save/close/check/configure/exit orchestration;
\item \texttt{SimulationController} validates simulation readiness before unsafe commands;
\item \texttt{SimulationCommandController} turns start/step/pause/resume/stop requests into simulator calls;
\item \texttt{SimulationEventController} bridges kernel simulation events back to the GUI;
\item \texttt{TraceConsoleController} renders simulator traces into the console, simulation, and reports panes;
\item \texttt{ModelInspectorController} keeps the component and data-definition trees synchronized with the scene;
\item \texttt{PropertyEditorController} binds scene selection to the property editor and coalesces post-commit refreshes;
\item \texttt{PluginCatalogController} owns the plugin tree presentation and insertion affordances;
\item \texttt{SceneToolController} owns zoom, drawing, animation, and layout commands;
\item \texttt{GraphicalContextMenuController} builds the scene context menu using existing actions;
\item \texttt{DialogUtilityController} owns the auxiliary dialogs and utility actions;
\item \texttt{GraphicalModelSerializer}, \texttt{GraphicalModelBuilder}, \texttt{ModelLanguageSynchronizer}, \texttt{GraphvizModelExporter}, and \texttt{CppModelExporter} keep persistence and representation work out of the widget code;
\item \texttt{GuiExtensionManager} rebuilds the extension surface from the loaded model plugins.
\end{itemize}

The important boundary is that these classes are not just helper functions. They are the current seam between the generated Qt widget tree and the rest of the application layer. In other words, the GUI already has a service/controller tier, but the legacy \texttt{MainWindow} wrappers still remain as compatibility glue.

\section{Signal, slot, and callback wiring}
\label{sec:gui-architecture-signals}

The GUI uses a mix of Qt signals/slots and explicit callback injection.

The direct Qt links still matter:
\begin{itemize}
\item \texttt{QAction} triggers map to legacy \texttt{MainWindow::on\_action...\_triggered()} slots;
\item \texttt{QGraphicsScene::changed}, \texttt{focusItemChanged}, and \texttt{selectionChanged} are connected back into \texttt{MainWindow} scene handlers;
\item the plugin tree, property editor tree, and several dialogs still use direct widget callbacks.
\end{itemize}

The extracted controllers then take over the heavier work through injected dependencies:
\begin{itemize}
\item \texttt{MainWindow} creates \texttt{ModelLifecycleController} with callbacks for console logging, model load/save, UI refresh, scene connection management, and textual synchronization;
\item \texttt{MainWindow} creates \texttt{SimulationCommandController} with callbacks for command logging, action refresh, model checking, text-to-simulation synchronization, and clearing simulation outputs;
\item \texttt{MainWindow} creates \texttt{PropertyEditorController} with callbacks for model-language refresh, component/data-definition refresh, C++ export refresh, model-image generation, and pane/action updates;
\item \texttt{MainWindow} creates \texttt{SimulationEventController} with callbacks for action refresh, event panes, debug tree refresh, and graphical-model refresh;
\item \texttt{ModelGraphicsView} accepts function callbacks for mouse, wheel, context-menu, and graphical-model event handling instead of hard-coding those paths in the widget class.
\end{itemize}

This is the main architectural fact to keep in mind when editing the GUI: the code is no longer a single nested slot file, but it is also not a pure signal-driven MVC stack. The current system is a controlled hybrid. Some behavior still routes through MainWindow wrappers, while the actual orchestration lives in small controllers and services.

\section{Model open and close flow}
\label{sec:gui-architecture-model-open}

The model lifecycle is managed by \texttt{ModelLifecycleController}, but the compatibility slot still lives in \texttt{MainWindow}.

The open flow currently works like this:
\begin{enumerate}
\item the user activates \texttt{on\_actionModelOpen\_triggered()} or a recent-file action;
\item \texttt{MainWindow} delegates to \texttt{ModelLifecycleController::onActionModelOpenTriggered()} or \texttt{openModelFile()};
\item the controller resolves the file path and prefers a companion \texttt{.gui} file when the input is a \texttt{.gen} file and a matching graphical file exists;
\item the controller logs the command into the console and calls the injected model-load callback;
\item after a successful load, the controller marks the model as loaded, rebuilds the UI for the new model, clears dirty flags, updates recent-file state, and clears the undo stack when available;
\item \texttt{MainWindow} then refreshes its recent-model menu and any dependent tabs or actions.
\end{enumerate}

The close flow stays in \texttt{MainWindow} for now, but it still interacts with the same lifecycle state:
\begin{itemize}
\item it checks whether the current model exists;
\item it closes only the current tab/model pair, not every loaded model;
\item it refreshes the action state after teardown.
\end{itemize}

This is a good example of the current compromise. The lifecycle orchestration is extracted, but the compatibility facade still hosts some tab and model-management behavior that has not yet been fully moved into the controller layer.

\section{Simulation action flow}
\label{sec:gui-architecture-simulation-flow}

Simulation actions use a two-layer guard:
\begin{enumerate}
\item \texttt{SimulationController} validates readiness, current-model existence, and the model-check/text-sync preconditions;
\item \texttt{SimulationCommandController} translates the action into start, step, pause, resume, or stop behavior and then calls \texttt{ModelSimulation}.
\end{enumerate}

The command controller also updates \texttt{AnimationTransition} flags and inserts the corresponding command into the console. That keeps simulation bookkeeping aligned with the textual command history and the graphical animation state.

Event reactions are handled separately by \texttt{SimulationEventController}:
\begin{itemize}
\item model-check success updates the graphical data-definition layer;
\item replication and simulation start/end events update the progress bar, event table, and tab state;
\item process and entity events drive the simulation and graphical progress paths;
\item the \texttt{setOnEventHandlers()} bridge registers the kernel callbacks through the compatibility facade.
\end{itemize}

Trace output is routed through \texttt{TraceConsoleController}, not through the simulation command path. That separation matters because trace rendering is presentation logic, while simulation commands are execution logic.

\section{Scene, property editor, and plugin catalog boundaries}
\label{sec:gui-architecture-boundaries}

Three GUI subsystems deserve separate mention because they are still coupled to the scene but no longer live entirely inside \texttt{MainWindow}:
\begin{itemize}
\item the plugin catalog is rebuilt from the kernel \texttt{PluginManager}, grouped by category, and kept as a drag source rather than a drop target;
\item the property editor syncs scene selection into \texttt{PropertyEditorGenesys} and \texttt{ObjectPropertyBrowser}, then defers heavy refreshes when a property commit is already in progress;
\item the graphics view owns the current \texttt{ModelGraphicsScene} wrapper and forwards context-menu, mouse, wheel, and selection events through injected callbacks.
\end{itemize}

That boundary is deliberately conservative. The GUI still uses scene-selection callbacks, direct widget refreshes, and a few legacy slots, but the meaningful logic is already in controller classes where it can be tested and reasoned about more locally.

\section{Current limitations}
\label{sec:gui-architecture-limitations}

The current snapshot has a few important limits:
\begin{itemize}
\item \texttt{MainWindow} is still the compatibility facade, so the GUI is not yet a fully clean presenter/service split;
\item several flows still rely on direct wrapper slots instead of a single modern event bus;
\item \texttt{ModelGraphicsView} and \texttt{ModelGraphicsScene} still expose a legacy callback-heavy interface because the scene interactions are not fully signal-based yet;
\item startup success does not prove that every GUI workflow is correct, only that the current wiring is coherent enough to initialize and delegate.
\end{itemize}

For maintainers, the practical rule is simple: change the extracted controller when the behavior is local to that responsibility, and change \texttt{MainWindow} only when the glue itself needs to change.
