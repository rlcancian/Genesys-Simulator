\chapter{Event Scheduling and Replications}
\label{chap:event-scheduling-and-replications}

This chapter documents the current event-driven execution core of GenESyS as
implemented in the repository. It does not invent a different scheduling model:
it explains the classes, methods, and callbacks that already exist in
\texttt{ModelSimulation}, \texttt{Event}, and \texttt{OnEventManager}.

\noindent\textbf{Objective.} Explain event scheduling, replication handling,
and their role in simulation control.

\noindent\textbf{Audience.} Developers who need to understand how the simulator advances time and repeats experiments.

\noindent\textbf{Scope.} Keep the chapter centered on events, replication
boundaries, event dispatch, observers, and the resulting runtime semantics.

\noindent\textbf{Status.} Partially validated by code inspection and the current
unit-test inventory. The chapter matches the current kernel and GUI callback
surface, but the visual figures are structural placeholders until the final
artwork is produced.

\section{The execution core}
\label{sec:event-scheduling-core}

The current simulation lifecycle is centered on \texttt{ModelSimulation}. That
class starts the simulation, starts each replication, advances the simulation
clock by processing events from the future-event list, and coordinates pause,
resume, step, and stop requests.

The object model is intentionally split. \texttt{Model} owns the structure of
the simulated system, including the future-event list. \texttt{ModelSimulation}
owns the execution state and the replication loop. \texttt{Event} represents a
scheduled instant, while \texttt{OnEventManager} exposes observation and
callback hooks around the runtime.

This separation matters because the simulator does not advance time in a simple
incrementing loop. It advances from scheduled event to scheduled event, and the
runtime state changes are concentrated in those event-processing points.

\section{The future-event list}
\label{sec:event-scheduling-future-event-list}

The future-event list is the kernel structure that drives event order. The
current implementation reads the first event from the list, treats it as the
next event to process, and removes it only when the event is actually
dispatched. The list is also cleared at the start of each replication to avoid
carrying stale queued events into the next run.

The implementation keeps the list sorted chronologically. When a new event is
created by the model or a component, it enters that list with the time stamp
that determines when it will become current.

The chapter should be read together with the kernel overview chapter, which
describes the future-event list as the central mechanism for chronological
progress.

\section{Replication lifecycle}
\label{sec:event-scheduling-replication-lifecycle}

Each simulation is composed of one or more replications. The current code
starts the simulation once, then starts each replication in order until the
replication count is exhausted or a stop/pause request interrupts the loop.

The first simulation startup performs common initialization:
\begin{itemize}
\item it checks the model before running;
\item it prepares the simulation header and tracing;
\item it computes the time-scale factor between replication and report units;
\item it creates the simulation-scoped statistics collectors and counters;
\item it sets the current replication number to one.
\end{itemize}

Each replication then performs its own initialization:
\begin{itemize}
\item pending events are destroyed and removed from the queue;
\item transient entities are removed from the model data manager;
\item simulated time is reset to zero;
\item per-replication model data is reinitialized;
\item source components are initialized after the remaining components;
\item statistics and counters are cleared when that option is enabled;
\item the replication-start observer notification is emitted.
\end{itemize}

The replication ends when one of the current end conditions is satisfied:
\begin{itemize}
\item the future-event list becomes empty;
\item the next event time goes beyond the configured replication length;
\item the terminating condition evaluates to true.
\end{itemize}

When a replication ends, the runtime emits the replication-end notification,
shows the replication report when enabled, and aggregates statistics into the
simulation-wide collectors.

\section{Event dispatch}
\label{sec:event-scheduling-dispatch}

The main event-processing path lives in \texttt{ModelSimulation::\_stepSimulation()}.
The current code emits a replication-step notification before it even removes
the next event from the queue. After that, it takes the next event, checks the
warm-up boundary when needed, evaluates breakpoints, and then either pauses or
processes the event.

For a normal event, the runtime does the following:
\begin{enumerate}
\item remove the event from the future-event list;
\item set the current event pointer;
\item update simulated time;
\item emit the process-event notification;
\item dispatch the event;
\item emit the after-process-event notification;
\item delete the processed event;
\item clear the current event pointer.
\end{enumerate}

The dispatch step distinguishes two paths:
\begin{itemize}
\item ordinary events are sent to \texttt{ModelComponent::DispatchEvent()};
\item internal events are handled by \texttt{InternalEvent::dispatchEvent()} and
are not tied to a specific entity/component move.
\end{itemize}

This distinction matters because the internal event path is used for kernel-side
callbacks that are unrelated to an entity traveling through a component.

\section{Observability and observers}
\label{sec:event-scheduling-observers}

\texttt{OnEventManager} is the callback hub for model and simulation events. It
stores handler lists for model check, load, save, replication start, replication
step, replication end, process event, after-process event, entity create, entity
move, entity remove, simulation start, simulation pause, simulation resume,
simulation end, and breakpoint notifications.

The class uses both function pointers and bound method handlers, and it
deduplicates handlers before insertion. The concrete tests in
\texttt{source/tests/unit/test\_support\_oneventmanager.cpp} exercise that
deduplication and method-dispatch behavior.

\texttt{SimulationEvent} carries the state that observers need to react to a
runtime notification: current event, current replication number, simulated
time, pause and stop flags, whether the simulation is running or paused, the
created entity, the destination component, and an optional custom object. The
model-level counterpart, \texttt{ModelEvent}, carries the current model.

The parser tests also prove that these callbacks are used during actual
simulation execution. In
\texttt{source/tests/unit/test\_parser\_expressions.cpp}, a replication-start
handler injects parser state before the process-event observer reads and writes
attributes during the run.

\section{Pause, resume, step, and breakpoints}
\label{sec:event-scheduling-pause-breakpoints}

The current runtime supports pause and resume as explicit simulation states.
\texttt{ModelSimulation::pause()} sets a pause request. \texttt{step()} is
implemented by forcing a temporary pause request, calling \texttt{start()}, and
then restoring the previous pause flag. \texttt{stop()} requests termination and
also performs a direct shutdown path when the simulation is already paused and
not running.

Breakpoints are supported on three dimensions:
\begin{itemize}
\item component;
\item entity;
\item time.
\end{itemize}

When a breakpoint matches the next event, the simulation emits the breakpoint
notification and pauses before processing the event. The code also guards
against immediately retriggering the same breakpoint twice in a row.

The GUI-facing execution states are still derived from the booleans in
\texttt{ModelSimulation} rather than from a dedicated enum. The supporting
behavior is exercised by the simulation startup smoke path in
\texttt{source/tests/smoke/smoke\_simulator\_start.cpp}, which confirms that the
simulator object initializes the core managers needed by the execution flow.

\section{Warm-up and termination}
\label{sec:event-scheduling-warmup-termination}

Warm-up is applied at the replication level. When a warm-up period is
configured, the next event is checked before processing. If the current
simulated time is still inside the warm-up window and the next event crosses
the boundary, the kernel clears the replication statistics so the initial
transient does not contaminate the measured results.

Termination is also replication-scoped. The kernel considers the event queue,
the replication-length horizon, and the terminating condition together. That is
why the chapter should not describe the run as ending only because a fixed
number of events have been executed. The configured replication length and the
optional terminating expression both matter.

\section{Cleanup and limits}
\label{sec:event-scheduling-cleanup-limits}

At the start of each replication, the kernel clears queued events and removes
transient entities before reinitializing the model data. After a processed
event, the code deletes the event only after the after-process notification so
observers can still inspect it.

The current implementation has a few explicit limits that the chapter should
state plainly:
\begin{itemize}
\item the event queue is owned by the model and is not a general-purpose event
broker;
\item internal events exist, but they are a separate path from ordinary entity
dispatch;
\item the experiment-oriented classes exist, but \texttt{ModelSimulation}
remains the operational execution core;
\item the GUI and the kernel share runtime state through boolean flags and
callbacks, not through a dedicated event-state enum.
\end{itemize}

The current test inventory provides support for the main flow categories but
does not prove every possible model, breakpoint, or terminating expression.
That boundary should remain explicit in the text.

\section{Validation anchors}
\label{sec:event-scheduling-validation-anchors}

The following tests support the main claims in this chapter:
\begin{itemize}
\item \texttt{source/tests/unit/test\_support\_oneventmanager.cpp} verifies
handler deduplication and method-handler dispatch in \texttt{OnEventManager};
\item \texttt{source/tests/unit/test\_parser\_expressions.cpp} exercises
replication-start and process-event callbacks during a real simulation run;
\item \texttt{source/tests/unit/test\_support\_simulationscenario.cpp} confirms
the current replication and control metadata model;
\item \texttt{source/tests/smoke/smoke\_simulator\_start.cpp} confirms the
simulator can construct the core managers needed by the execution path.
\end{itemize}

These tests validate the callback surface and startup path, but they do not
replace code inspection for exact event order, breakpoint behavior, or the
precise replication termination conditions.
