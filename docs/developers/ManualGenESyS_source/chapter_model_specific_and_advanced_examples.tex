\chapter{Model-Specific and Advanced Examples}
\label{chap:model-specific-and-advanced-examples}

This chapter documents the current model-specific application route as it
exists in the repository today. It does not invent a generic "advanced
examples" story. Instead, it explains how the build selects one concrete
example, how the legacy compatibility path behaves, which example families
exist in the tree, and which examples were actually reproduced during this
revision.

\noindent\textbf{Objective.} Explain the model-specific build route, show the
current example catalog, and document a small set of reproducible advanced
examples.

\noindent\textbf{Audience.} Advanced users, instructors, and maintainers who
need concrete example flows beyond the introductory user chapters.

\noindent\textbf{Scope.} Cover the current CMake selection mechanism, the
legacy compatibility alias, the example catalog under
\path{source/applications/modelSpecific}, the reproduced example outputs, and
the maturity boundaries of the remaining historical examples.

\noindent\textbf{Status.} Partially validated against the current branch. Two
examples were reproduced successfully in this revision, while one historical
smarts example still shows a runtime crash and is therefore documented as a
limitation rather than a supported flow.

\section{How the build selects one example}
\label{sec:model-specific-selection}

The model-specific route is build-time selected. The current CMake logic in
\path{source/applications/modelSpecific/CMakeLists.txt} accepts a relative
source path through \path{GENESYS_MODELSPECIFIC_APP}. The optional
\path{GENESYS_MODELSPECIFIC_APP_CLASS} and
\path{GENESYS_MODELSPECIFIC_APP_HEADER} variables allow the build to override
the class name or header name when the source stem does not match the actual
symbols. The deprecated aliases
\path{GENESYS_TERMINAL_EXAMPLE} and
\path{GENESYS_TERMINAL_EXAMPLE_CLASS} remain accepted for compatibility, but
they map back to the newer names and are documented as legacy inputs.

The build target is \path{genesys_modelspecific_app}. After the executable is
built, the post-build step creates a compatibility copy named
\path{genesys_terminal_application}. That copy preserves the older launch name
for workflows that still expect it, but the canonical target is the newer
model-specific one.

The selected source must stay inside
\path{source/applications/modelSpecific}, must end in \path{.cpp}, and must
have a matching header file. The selected binary links the shared kernel,
parser, plugin, simulator-support, and simulator-runtime libraries, so the
runtime behavior depends on the exact source file chosen at configure time.

\section{Current example catalog}
\label{sec:model-specific-catalog}

The current tree contains multiple families of model-specific applications.
The practical split is by teaching style and maturity:
\begin{itemize}
\item \textbf{arenaExamples} are the clearest user-facing examples. They tend
to save a \path{.gen} file and then run the model immediately.
\item \textbf{smarts} are compact capability exercises. Some save a model, some
exist mainly to exercise a feature path, and some are still historical
snapshots that need revalidation.
\item \textbf{teaching} and \textbf{wcm} examples are present in the tree and
serve more specialized educational or scientific purposes, but they are not
the focus of this chapter.
\end{itemize}

The override file \path{source/applications/modelSpecific/modelSpecificApps.tsv}
captures special cases that the build script should treat conservatively. In
this revision it records the modal-model examples that need class or header
adjustments and distinguishes generators from validation-only exercises.

\subsection{Reproducible generator examples}
\label{subsec:model-specific-reproducible-examples}

Two examples were reproduced successfully in this revision with the helper
script \path{scripts/regenerate-models-from-modelspecific.sh} and the
\path{genesys_modelspecific_app} preset:
\begin{itemize}
\item \textbf{\path{arenaExamples/AirportSecurityExample.cpp}.} This example
generated \path{./models/AirportSecurityExample.gen}. The runtime built a small
flow around \texttt{Create}, \texttt{Process}, \texttt{Decide}, and
\texttt{Dispose}, then completed two replications of a 12 hour run.
\item \textbf{\path{arenaExamples/Banking_Transactions.cpp}.} This example
generated \path{./models/Banking_Transactions.gen}. The runtime completed
three replications of an 8 hour run and exercised a richer mix of
\texttt{Station}, \texttt{Enter}, \texttt{Route}, \texttt{Seize},
\texttt{Delay}, and \texttt{Release}.
\end{itemize}

Both examples are useful because they show a real advanced-user boundary: the
model-specific executable is not a generic launcher, but a concrete generator
that saves a model file and then runs it immediately.

\subsection{Historical smarts and maturity boundaries}
\label{subsec:model-specific-maturity}

The modal-model smarts are still present in the tree and are worth keeping in
the chapter because they exercise the selection overrides described earlier.
However, they do not all have the same maturity.

\begin{itemize}
\item \path{smarts/ModalModel/Smart_Modalmodel.cpp} saves
\path{./models/Smart_ModalModel.gen} and uses \texttt{ModalModelDefault}, but
the current validation run ended with a segmentation fault during simulation.
That makes it a snapshot example, not a supported advanced flow yet.
\item \path{smarts/ModalModel/Smaty_DefaultModalModel.cpp} is the historical
stem-typo case that resolves to the \texttt{Smart\_DefaultModalModel} class
through header/class overrides. It remains in the catalog because the build
logic still needs to support that legacy naming pattern.
\end{itemize}

The practical lesson is simple: a source file being present in the model-
specific tree does not automatically mean it is mature enough to recommend
without qualification.

\section{Usage boundary}
\label{sec:model-specific-boundary}

Use the model-specific route when you want a concrete compiled example rather
than the general shell or GUI front ends. The route is a good fit for:
\begin{itemize}
\item teaching a specific workflow around a known model;
\item validating a model-specific source file against the current branch;
\item regenerating a \path{.gen} file from a concrete example source;
\item checking whether a historical example still runs on the current code.
\end{itemize}

Do not treat this route as a general plugin loader or as a guarantee that all
example files in the tree are equally maintained. The current validation sweep
shows that some examples are stable enough to reproduce, while others still
need repair or revalidation before they can be recommended.

In short: choose a model-specific example when the source itself is the thing
you want to compile and run. Choose the GUI or shell when the task is general
model editing or interactive simulation work.
