\chapter{Running Simulations}
\label{chap:running-simulations}

This chapter documents the current simulation-execution surface of
\texttt{genesys-gui} as it exists in the repository. The goal is not to invent a
new execution model, but to explain the commands, states, and breakpoint
surfaces already wired into the GUI and kernel.

\noindent\textbf{Objective.} Document the visible steps required to launch,
pause, resume, step through, and stop a simulation run.

\noindent\textbf{Audience.} Users who already have a model loaded and want to
execute it safely.

\noindent\textbf{Scope.} Cover the simulation configuration dialog, the run
commands, the derived execution states, breakpoint handling, the standard
start-to-end flow, and the current limitations of the local execution path.

\noindent\textbf{Status.} Partially validated by code inspection. The chapter
matches the current GUI labels and kernel methods, but the visual figures are
still placeholders until the final screenshots are produced.

\section{Configuring a simulation run}
\label{sec:running-simulations-configuring}

The simulation dialog is opened through \texttt{actionSimulationConfigure} and
is titled \textit{Configure Simulation}. Its current content is split into
three tabs: \textit{Model Simulation}, \textit{Simulation Report}, and
\textit{Parallelization}. The first tab contains the operational controls that
matter for a local run:
\begin{itemize}
\item \textit{Number of Replications};
\item \textit{Replication Base Time Unit};
\item \textit{Replication Length};
\item \textit{Warmup Period};
\item \textit{Terminating Condition};
\item \textit{Initialize system};
\item \textit{Initialize statistics between replications};
\item \textit{Step by step};
\item \textit{Pause on event};
\item \textit{Pause on replication}.
\end{itemize}

The dialog mirrors the live \texttt{ModelSimulation} object rather than a
static copy. That matters because the current kernel stores the same execution
parameters that the GUI exposes: replication count, replication length,
time-unit metadata, warm-up period, terminating condition, and the boolean
pause/initialization flags.

The dialog also contains a \textit{Simulation Report} tab. In the current code
that tab is read-only from the GUI point of view: it reports whether a
\texttt{SimulationReporter\_if} instance is loaded, but it does not expose
editable reporter controls yet.

The \textit{Parallelization} tab should be read conservatively. The local
parallelization fields are real GUI state, but the distributed button is a
placeholder that only explains the intended future integration path. For this
chapter, the supported execution path is the local one.

The chapter does not invent a dedicated seed field here. The current dialog and
kernel surface do not expose a direct seed control in this path, so any run
record that needs reproducibility must keep the seed from the surrounding
execution environment or from the model-generation context.

\section{Simulation states and commands}
\label{sec:running-simulations-states}

The current implementation does not expose a dedicated enum for the user-facing
simulation state. Instead, the GUI derives the visible state from
\texttt{ModelSimulation::isRunning()} and \texttt{ModelSimulation::isPaused()},
while the kernel transitions are driven by \texttt{start()},
\texttt{pause()}, \texttt{step()}, and \texttt{stop()}.

The practical state machine is:
\begin{itemize}
\item \textit{Idle or ready}: no run is active yet;
\item \textit{Running}: the simulation loop is processing events and
replications;
\item \textit{Paused}: the run was interrupted by a pause request, a step
request, or a breakpoint;
\item \textit{Ended}: the simulation completed or was stopped.
\end{itemize}

The command behavior is conservative and direct:
\begin{itemize}
\item \texttt{Start} checks the model, initializes the simulation if needed,
and then runs replications until the end condition is met;
\item \texttt{Pause} requests a pause at the next safe point;
\item \texttt{Resume} reuses the start path while the simulation is paused;
\item \texttt{Step} requests one event step and then returns to the paused
state if the run remains open;
\item \texttt{Stop} requests termination and clears the paused state when the
simulation is already suspended.
\end{itemize}

The GUI menu and toolbar reflect those same states. While the simulation is
running or paused, the code disables structural model editing, most view
manipulation, and property editing. That lock is deliberate: the runtime state
must not be mutated by concurrent model edits.

\section{Breakpoints and pause policies}
\label{sec:running-simulations-breakpoints}

Breakpoints are exposed separately from the pause buttons. The current kernel
supports breakpoints on:
\begin{itemize}
\item components;
\item entities;
\item simulation time.
\end{itemize}

Those breakpoints are listed in the Breakpoints tab through the
\texttt{tableWidget\_Breakpoints} surface. The table is populated from the live
\texttt{ModelSimulation} breakpoint lists exposed by
\texttt{getBreakpointsOnComponent()}, \texttt{getBreakpointsOnEntity()}, and
\texttt{getBreakpointsOnTime()}.

Breakpoint handling is event-driven. When an event matches a component, entity,
or time breakpoint, the simulation emits the breakpoint notification, traces a
pause message, and suspends the run. The implementation also guards against
retriggering the same time breakpoint back-to-back.

The pause-related checkboxes in the configuration dialog are different from
breakpoints:
\begin{itemize}
\item \textit{Step by step} makes the simulation behave like a one-event loop;
\item \textit{Pause on event} requests a pause after event handling;
\item \textit{Pause on replication} requests a pause between replications.
\end{itemize}

That distinction matters. Breakpoints are selective stop conditions. The pause
flags are execution policies. The user can combine them, but they are not the
same feature.

\section{Start-to-end execution flow}
\label{sec:running-simulations-sequence}

A clean execution sequence in the current GUI is:
\begin{enumerate}
\item load a model;
\item open \textit{Configure Simulation};
\item confirm the number of replications, replication length, warm-up period,
and terminating condition;
\item decide whether step-by-step, pause-on-event, or pause-on-replication
should be enabled;
\item start the simulation;
\item observe the trace and runtime feedback;
\item pause, step, or resume if a breakpoint or manual pause is needed;
\item stop the run when the result is sufficient.
\end{enumerate}

The main guarantee here is that the command sequence matches the runtime
locking rules. When the run is active, editing surfaces are disabled. When the
run is paused, the simulation can still be resumed or stepped. When the run is
done, the GUI returns to the normal editing state.

The chapter's working rule is simple: do not treat a run as correct merely
because it started. A correct run is one where the configuration dialog,
command behavior, state transitions, and breakpoint behavior all line up with
the kernel implementation.

\section{Current limitations}
\label{sec:running-simulations-limitations}

This chapter intentionally stays within the currently supported local execution
surface.
\begin{itemize}
\item The distributed parallelization controls are present as GUI structure, but
the dialog still treats them as a future path rather than a finished runtime.
\item The simulation seed is not exposed as a dedicated control in this dialog.
\item The chapter does not claim a universal execution policy for all future
experiment abstractions.
\item The visual figures remain placeholders until the final screenshots are
produced.
\end{itemize}

Those limitations are not defects in the chapter. They are the boundary between
what the current repository actually supports and what the manual should not
overstate.
