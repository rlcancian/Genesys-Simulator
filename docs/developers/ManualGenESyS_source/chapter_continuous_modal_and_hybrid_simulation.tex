\chapter{Continuous, Modal, and Hybrid Simulation}
\label{chap:continuous-modal-and-hybrid-simulation}

This chapter documents the current continuous, modal, and hybrid simulation
surface in the repository as it exists now. It is intentionally conservative:
the text distinguishes implemented support from historical scaffolding and does
not claim a unified scientific validation package that the codebase does not
yet provide.

\noindent\textbf{Objective.} Explain the continuous solver layer, the
Method-of-Lines diffusion bridge, the modal-model and Petri-net facilities,
the cellular-automata helpers, and the way these pieces interact with the
discrete-event clock.

\noindent\textbf{Audience.} Developers and advanced modelers who need to reason
about multi-mode simulation behavior, model-to-solver coupling, and the current
validation boundary.

\noindent\textbf{Scope.} Cover the ODE solver factory, the diffusion PDE
implementation, modal networks, Petri nets, cellular automata, the current
hybrid bridges, and the limits of what can be claimed from the available code
and tests.

\noindent\textbf{Status.} Substantive documentation grounded in
\path{source/tools/Continuous}, \path{source/plugins/components/ModalModel},
\path{source/plugins/data/Continuous}, and the current regression tests. The
chapter treats numerical accuracy claims as demonstrative unless a test or
reference in the repository establishes more.

\section{Continuous solver layer}
\label{sec:continuous-solver-layer}

The current continuous-simulation layer is split into a legacy solver contract
and a more explicit ODE abstraction. In the tree today, \texttt{Solver\_if} and
\texttt{SolverDefaultImpl1} remain as compatibility material, while
\texttt{OdeSolver\_if}, \texttt{OdeSystem\_if}, and
\texttt{OdeSolverFactory} define the clearer ODE-oriented path. The factory
currently registers \texttt{RungeKutta4} and \texttt{DormandPrince54}; those
are the concrete solver names that the code and tests can resolve today.

\subsection{Solver selection and runtime coupling}
\label{subsec:continuous-solver-selection}

The ODE-oriented path is centered on \texttt{OdeSolverFactory}. That factory
creates a solver object from a string key or enum value, and the
\texttt{DiffusionField} plugin uses that selection mechanism to choose between
the supported solver names. The current evidence is direct: the headers in
\path{source/tools/Continuous} define the factory and concrete solvers, and the
regression tests exercise both supported solver keys.

The runtime coupling is easier to understand when viewed as a sequence rather
than a single class:
\begin{itemize}
\item a model or helper selects a solver name;
\item the factory materializes a concrete solver object;
\item the solver advances a system of equations over a time step;
\item the calling component records or propagates the new state;
\item the discrete-event kernel remains responsible for the event clock.
\end{itemize}

\section{Diffusion and Method of Lines}
\label{sec:diffusion-and-method-of-lines}

The diffusion path is the clearest current example of a continuous PDE bridge
inside GenESyS. The kernel-facing plugin is \texttt{DiffusionField}; it solves
\(du/dt = D \nabla^2 u\) in \(N\) dimensions using a dedicated
\texttt{DiffusionMethodOfLinesSystem}. Spatial discretization is handled by the
Method of Lines, and time stepping is delegated to the selected ODE solver from
the factory.

The component counterpart is \texttt{DiffusionSimulate}. It acts as a
discrete-to-continuous bridge: when an entity arrives, it can trigger a
diffusion solve using either the field's own configured window or the
component's override window. The field itself also supports event-driven
advancement via internal events when \texttt{AutoSchedule} is enabled, so the
continuous solve can stay synchronized with the kernel clock.

solver or grid settings are rejected.

\subsection{What the diffusion tests prove}
\label{subsec:diffusion-tests}

The strongest direct evidence for the diffusion path is
\path{source/tests/unit/test_plugins_continuous_diffusion.cpp}. That test file
confirms all of the following in the current tree:
\begin{itemize}
\item the default solver is \texttt{RungeKutta4};
\item the analytical decay of a sine mode matches the discretized evolution to
  the current test tolerance;
\item \texttt{RungeKutta4} and \texttt{DormandPrince54} produce comparable
  results on the same setup;
\item Neumann boundary conditions conserve total mass within the current test
  tolerance;
\item the implementation runs in three dimensions;
\item configuration round-trips through persistence;
\item invalid solver and invalid grid or boundary settings are rejected;
\item the \texttt{DiffusionSimulate} component can drive the field.
\end{itemize}

Those checks are strong runtime evidence, but they are still evidence for the
specific scenarios under test. They are not a claim that every diffusion
boundary condition, every solver, or every grid size has been scientifically
validated.

\section{Modal models and hybrid execution}
\label{sec:modal-and-hybrid-execution}

The modal-model layer groups several related formalisms under the same
component family. \texttt{ModalModelDefault} is the base network container.
\texttt{ModalModelFSM} extends it with finite-state semantics, while
\texttt{ModalModelPetriNet} extends it with Petri-net semantics. The transition
helpers also remain explicit: \texttt{EFSMTransition} carries trigger and
probability semantics, and \texttt{PetriTransition} carries token-based input
and output arc weights.

This is the right place to keep the boundary clear:
\begin{itemize}
\item an FSM transition is not the same thing as a Petri transition;
\item the model holds the state and transition topology;
\item the current code keeps the semantics in dedicated classes instead of
  collapsing everything into one generic transition type;
\item the chapter does not claim a finished unified modal runtime beyond what
  the classes in the tree actually implement.
\end{itemize}

path.

\subsection{Petri nets}
\label{subsec:petri-nets}

The Petri-net side is concrete enough to document directly. \texttt{PetriPlace}
stores token counts by color, and \texttt{PetriTransition} checks and moves
those tokens between places according to its input and output arc weights.
That is a real enable/fire model, not a generic placeholder.

The model-specific examples in \path{source/applications/modelSpecific/smarts/ModalModel}
show that path in a runnable form. The current tree includes examples for a
default modal network, an FSM, and Petri-based examples such as

\section{Cellular automata}
\label{sec:cellular-automata}

Cellular automata are also present in the modal-model area, but they have their
own dedicated component and runtime helpers. The component facade is
\texttt{CellularAutomataComp}, which can be configured as classic, timed 1D,
asynchronous, or user-defined. The underlying helper types include
\texttt{CellularAutomataBase}, \texttt{CellularAutomata}, \texttt{Lattice},
\texttt{Neighborhood}, \texttt{StateSet}, and a set of local rules such as
Game of Life, HPP lattice gas, sand/rock, forest fire, and related examples.

The important distinction is that the tree contains multiple CA helpers, but
they do not all represent the same execution model:
\begin{itemize}
\item \texttt{CellularAutomata\_Classic} applies the same local rule to all
  cells and then updates their states;
\item \texttt{CellularAutomata\_1DTimed} treats the second dimension as time;
\item the component facade carries configuration for lattice, neighborhood,
  boundary, state set, and local rule selection;
\item the current classes are supportive infrastructure, not a claim that every
  automaton family is fully polished or equally validated.
\end{itemize}

\section{Hybrid coupling and validation boundary}
\label{sec:hybrid-coupling-and-validation}

The hybrid-simulation story is the interaction between the discrete-event
calendar and the continuous or modal submodels. The current code supports that
interaction in several ways:
\begin{itemize}
\item \texttt{DiffusionField} can auto-schedule internal events so the field
  advances one step per kernel event;
\item \texttt{DiffusionSimulate} can launch a diffusion solve when an entity
  arrives at the component;
\item \texttt{ContinuousSystemComponent} and the ODE examples show how a
  continuous solver can be driven from a discrete-event workflow;
\item the model-specific continuous trace example demonstrates that solver time
  and simulated time are related but not identical concepts.
\end{itemize}

The correct mental model is that the discrete-event kernel owns the event
clock, while the continuous subsystem owns its internal state and step policy.
Fixed-step advancement is therefore not automatically equivalent to elapsed
discrete-event time. That distinction is documented in the scientific-domain
reference and is visible in the trace example.

\subsection{Current validation boundary}
\label{subsec:current-validation-boundary}

The current tree gives enough evidence to document the implemented behavior,
but not enough to claim global numerical certification. The supported and
demonstrated points are:
\begin{itemize}
\item explicit ODE solver selection works through the factory;
\item diffusion examples can be reproduced and checked against the current
  analytical reference in the tests;
\item modal-network, Petri, and CA helpers exist and are wired into the source
  tree;
\item event-clock coupling is implemented for the documented diffusion and
  continuous-system examples;
\item the chapter does not extend those results into a general scientific
  validity claim for all future models.
\end{itemize}

Historical LSODE-based examples still exist in the tree, including
\path{source/tests/test_lsode.cpp} and the model-specific continuous examples
under \path{source/applications/modelSpecific/smarts/Continuous}. They are
useful as legacy context, but the explicit ODE solver factory and the diffusion
bridge are the clearest current support surface for this chapter.

That is the right level of claim for the current manual revision: the feature
families are real, the coupling is real, and the validation is real for the
scenarios already tested, but the codebase still contains experimental and
historical areas that should remain labeled as such.
