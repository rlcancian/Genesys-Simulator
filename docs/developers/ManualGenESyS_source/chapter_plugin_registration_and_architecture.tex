\chapter{Plugin Registration and Architecture}
\label{chap:plugin-registration-and-architecture}

This chapter documents the plugin boundary as it exists in the current code
base. The key point is simple: GenESyS still uses plugins as a structural
extension mechanism, but the present implementation is organized as static
libraries and build-time aggregation, not as a separate dynamic-plugin
runtime.

\noindent\textbf{Objective.} Explain the current plugin architecture, how the
build registers it, and which parts are only planned for a future dynamic
model.

\noindent\textbf{Audience.} Developers who need to understand how the current
repository assembles plugin code and where the architectural debt still lives.

\noindent\textbf{Scope.} Cover the CMake target map, the current registration
and metadata flow, the lifecycle of plugin code in the build, and the planned
future architecture. The future state is described as planned only; it is not
presented as implemented behavior.

\noindent\textbf{Status.} Current architecture documented from the live CMake
layout and the kernel/plugin manager boundary. The dynamic-plugin future is a
design target, not a shipped capability.

\section{Current plugin architecture}
\label{sec:plugin-current-architecture}

In the current repository, the plugin layer is assembled at build time. The
root plugin CMake file:
\begin{itemize}
 \item adds the \texttt{data} and \texttt{components} subdirectories;
 \item defines the aggregate static library
   \texttt{genesys\_plugins\_components\_minimal}.
\end{itemize}

This means the current plugin model is a static-linking architecture with
clear internal grouping, not a runtime loader that discovers shared objects
on disk.

The current target map is:
\begin{itemize}
 \item \texttt{genesys\_plugins\_data}: static library with the plugin-side
   data definitions;
 \item \texttt{genesys\_plugins\_components}: static library with the broader
   component set;
 \item \texttt{genesys\_plugins\_components\_minimal}: static aggregate over
   the component sources in \texttt{source/plugins/components/}.
\end{itemize}

The data library links to \texttt{genesys\_kernel\_util} and
\texttt{genesys\_ai\_provider}. It also carries the
\texttt{GENESYS\_HAS\_PYTHON\_INTEGRATION} definition and conditionally links
to \texttt{Python3::Python} when Python integration is enabled. The component
library links to \texttt{genesys\_kernel\_util} and
\texttt{genesys\_plugins\_data}, and it optionally uses GLPK when the system
dependency is available. That optional dependency is still resolved at build
time.

The kernel side also reflects this design. The simulator still exposes a
\texttt{PluginManager}, but the code base does not describe a separate
dynamic-plugin package boundary. The practical meaning is that plugin
registration today is mostly a question of how the build assembles and links
static libraries, how metadata is surfaced, and how the kernel keeps track of
the connected plugin wrappers.

\subsection{Registration and metadata flow}
\label{subsec:plugin-registration-metadata}

The current registration flow is build-first:
\begin{itemize}
 \item source files are grouped under the plugin subtrees;
 \item CMake turns those sources into static libraries;
 \item the application targets link those libraries into the final binaries;
 \item the kernel/plugin manager layer consumes the resulting plugin
   metadata and connected wrappers.
\end{itemize}

That flow matters because it keeps registration deterministic. There is no
claim here that a plugin can be dropped into a runtime directory and loaded as
an independent shared object. The existing model is closer to a curated
compile-and-link registry than to a late-bound extension loader.

the manual. Components and data definitions live in the plugin tree, but their
lifecycles are controlled by the normal build and object-graph rules of the
current code base. In other words, the plugin layer is an extensibility
mechanism, yet it is still embedded in the build graph.

\section{Current lifecycle}
\label{sec:plugin-current-lifecycle}

The lifecycle of a plugin in the current implementation has three distinct
stages.

\begin{enumerate}
 \item \textbf{Build stage.} CMake discovers the sources, defines the static
   libraries, and resolves optional dependencies such as Python integration and
   GLPK.
 \item \textbf{Link stage.} The selected applications and test targets link
   the plugin libraries into the final executable or test binary.
 \item \textbf{Kernel stage.} The simulator starts with the linked plugin code
   already present, and the kernel/plugin manager boundary exposes the loaded
   metadata and connected wrappers to the rest of the system.
\end{enumerate}

The important architectural consequence is that plugin availability is
decided before runtime. This keeps the current system predictable, but it also
means that a future dynamic model would require a genuine boundary decision
around loading, discovery, visibility and compatibility. The code base does
not claim that boundary today.

The current lifecycle also explains the main failure modes. A plugin problem is
usually a build, dependency, or linkage issue, not a runtime installation
problem in the sense of a separate plugin package. That distinction is useful
because it prevents the reader from assuming a deployable plugin ecosystem
that the repository does not yet provide.

\section{Future plugin architecture}
\label{sec:plugin-future-architecture}

The future architecture discussed in this chapter is explicitly planned. It is
not implemented, and no stable ABI is claimed.

The planned direction includes:
\begin{itemize}
 \item dynamic plugins loaded from separate artifacts;
 \item explicit factories for plugin discovery and instantiation;
 \item versioned metadata and compatibility checks;
 \item controlled symbol visibility and export policy;
 \item packaging rules for plugin distribution;
 \item isolation boundaries for safer loading and failure handling;
 \item a documented ABI strategy if and when the project chooses one.
\end{itemize}

These points are architectural goals, not current behavior. In particular, the
repository does not yet provide a stable dynamic-plugin ABI, and the text in
this chapter must not be read as implying one.

The most important debt item here is the ABI question. A future ABI boundary
cannot be improvised from the current static-linking model. It needs an
explicit decision about versioning, symbol export, compatibility guarantees,
and the level of isolation expected from a plugin package. Until that happens,
the conservative reading is the correct one: the current repository uses static
plugin aggregation.

\subsection{Architectural debt}
\label{subsec:plugin-architectural-debt}

The chapter records the following open debts so that the future work does not
silently overclaim what is already available:
\begin{itemize}
 \item no dynamic loader is present yet;
 \item no stable plugin ABI is documented or implemented;
 \item no packaging contract for standalone plugin artifacts exists yet;
 \item no runtime compatibility matrix is enforced yet;
 \item no isolation model for untrusted plugin code is defined yet.
\end{itemize}

\section{Current versus future}
\label{sec:plugin-current-vs-future}

The simplest way to read the boundary is to compare the current and planned
models directly:

\begin{itemize}
 \item \textbf{Current.} Static libraries, build-time aggregation, linked
   metadata, and kernel-facing plugin wrappers already present in the binary.
 \item \textbf{Future.} Dynamic artifacts, explicit discovery, factories,
   compatibility checks, packaging, and ABI control.
\end{itemize}

This comparison is intentionally asymmetric. The current side is factual; the
future side is a roadmap. The manual should keep that distinction visible so
that readers do not confuse a planned extensibility direction with a shipped
runtime feature.

\section{What this chapter deliberately does not claim}
\label{sec:plugin-does-not-claim}

This chapter deliberately avoids three overclaims:
\begin{itemize}
 \item that GenESyS already ships a dynamic plugin runtime;
 \item that the plugin ABI is frozen;
 \item that loading, packaging, and compatibility are solved for third-party
   runtime plugin distribution.
\end{itemize}

Those are future decisions. The current code base documents a static plugin
architecture with build-time aggregation and a kernel-facing metadata layer.
That is enough to support the repository as it exists today, and it is the
correct foundation for the next phase of the work.
