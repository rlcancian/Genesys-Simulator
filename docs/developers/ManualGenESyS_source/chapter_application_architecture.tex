\chapter{Application Architecture}
\label{chap:application-architecture}

This chapter documents the current application architecture as it exists in
the active branch and current CMake files on 2026-07-23. It is based on the
root \texttt{README.md}, the root \texttt{CMakeLists.txt}, the application and
tools CMake files, and the observed entry points in \texttt{source/applications}
and \texttt{source/tools}. It describes the current process boundaries and
shared backends, not a future idealized layout.

\noindent\textbf{Objective.} Explain how the current executable applications
are composed, which shared libraries they use, and where the process
boundaries sit.

\noindent\textbf{Audience.} Developers who need a faithful map of the current
application layer before changing startup code, target wiring, shared
libraries, or deployment assumptions.

\noindent\textbf{Scope.} Cover executable families, composition roots,
shared libraries, process boundaries, configuration flags, startup/shutdown
paths, and the most visible error exits. Keep the discussion limited to the
current code tree and the current CMake build surface.

\noindent\textbf{Status.} Confirmed by repository inspection on 2026-07-23.
The chapter describes the current architecture snapshot, not a planned future
state.

\section{Current executable families}
\label{sec:application-architecture-families}

The current application layer is a set of separate executables, not one
monolithic process. The build surface currently exposes these runtime
families:
\begin{itemize}
\item the command-line shell, \texttt{genesys\_shell};
\item the worker runtime, \texttt{genesys\_worker\_app}, with the executable
name \texttt{genesys-worker} and the alias target \texttt{genesys\_worker};
\item the main Qt GUI, \texttt{genesys\_gui\_application}, with the executable
name \texttt{genesys-gui} and the alias target \texttt{genesys\_gui};
\item the HTTP Worker GUI, \texttt{genesys\_httpworker\_gui\_application}, with
the executable name \texttt{genesys-httpworker-gui};
\item the Data Analyser, \texttt{genesys\_dataanalyser\_gui\_application}, with
the executable name \texttt{genesys-dataanalyser-gui};
\item the Optimizer, \texttt{genesys\_optimizer\_gui\_application}, with the
executable name \texttt{genesys-optimizer-gui};
\item the AI Assistant, \texttt{genesys\_ai\_assistant\_gui\_application}, with
the executable name \texttt{genesys-ai-assistant-gui};
\item the model-specific route, \texttt{genesys\_modelspecific\_app}, with the
compatibility copy \texttt{genesys\_terminal\_application};
\item the optional tools CLI, \texttt{genesys\_tools\_application}, which is a
support entry point rather than a user-facing simulation frontend.
\end{itemize}

The current GUI umbrella also keeps a planned-but-not-implemented
\texttt{GENESYS\_BUILD\_GUI\_DOEXPERIMENTS} flag. That flag is a guarded
absence, not a runnable process.

\section{Composition roots}
\label{sec:application-architecture-composition-roots}

Each executable owns its own composition root. The startup code is intentionally
local to the process so that one application cannot silently depend on another
application's window or event loop.

\subsection{Shell}
\label{subsec:application-architecture-shell}

The shell uses a minimal console bootstrap: \texttt{main.cpp} creates the
selected terminal application and forwards \texttt{argc}/\texttt{argv} to its
\texttt{main()} method. The current implementation keeps the entry point
generic through \texttt{GENESYS\_TERMINAL\_APP\_CLASS} and
\texttt{GENESYS\_TERMINAL\_APP\_HEADER}.

\subsection{Worker}
\label{subsec:application-architecture-worker}

The worker executable constructs \texttt{BaseGenesysWebApplication} and then
enters its HTTP serve loop. The worker bootstrap creates
\texttt{TokenService}, \texttt{SessionManager}, \texttt{WorkerJobManager},
\texttt{SimulatorSessionService}, \texttt{ApiRouter}, and
\texttt{SimpleHttpServer} before it starts listening.

\subsection{Main GUI}
\label{subsec:application-architecture-main-gui}

The main GUI installs crash and logging handlers, creates a
\texttt{QApplication}, loads system preferences, applies the theme, builds the
main window, and then enters the Qt event loop. That bootstrap is the
composition root for the primary desktop process.

\subsection{Standalone Qt frontends}
\label{subsec:application-architecture-standalone-frontends}

The HTTP Worker GUI, Data Analyser, Optimizer, and AI Assistant each keep
their own \texttt{main.cpp} and their own Qt application object. The GUI
umbrella only selects which executable target is built; it does not merge
those windows into one binary.

\subsection{Model-specific route and tools CLI}
\label{subsec:application-architecture-modelspecific-tools}

The model-specific route is build-time selected through
\texttt{GENESYS\_MODELSPECIFIC\_APP} and related overrides. Its bootstrap
creates the selected terminal application class and then runs it as a separate
process. The optional tools CLI is simpler: it prints the supported tool
interfaces for \texttt{--list} or \texttt{--help}, and exits with an error for
unknown commands.

\section{Shared libraries and services}
\label{sec:application-architecture-shared-libraries}

The current architecture reuses a small set of static libraries across
multiple processes:
\begin{itemize}
\item \texttt{genesys\_kernel\_util};
\item \texttt{genesys\_kernel\_statistics};
\item \texttt{genesys\_parser};
\item \texttt{genesys\_plugins\_data};
\item \texttt{genesys\_plugins\_components\_minimal};
\item \texttt{genesys\_kernel\_simulator\_support};
\item \texttt{genesys\_kernel\_simulator\_runtime};
\item \texttt{genesys\_worker\_core};
\item \texttt{genesys\_tools}.
\end{itemize}

The first seven libraries form the common simulator backbone. They are static
libraries and aggregate build targets, not runtime plugin processes. The worker
stack adds \texttt{genesys\_worker\_core}, which contains
\texttt{ApiRouter}, \texttt{TokenService}, \texttt{SimpleHttpServer},
\texttt{WebWorkerRuntime}, \texttt{SimulatorSessionService},
\texttt{SessionManager}, and \texttt{WorkerJobManager}. The tools stack adds
\texttt{genesys\_tools}, which groups the assistant, statistics, optimization,
continuous, and factorial-design backends and links \texttt{genesys\_ai\_provider}.

The main GUI links both \texttt{genesys\_worker\_core} and
\texttt{genesys\_tools}, which is why its UI can reuse worker-facing and
analysis-facing support code without collapsing those flows into a single
process. The HTTP Worker GUI links only \texttt{genesys\_worker\_core}; the
Data Analyser, Optimizer, and AI Assistant link \texttt{genesys\_tools} and the
shared simulator backbone.

\section{Process boundaries and configuration}
\label{sec:application-architecture-process-boundaries}

Every executable listed above is a separate operating-system process. Linking a
library into a process does not erase the boundary, and no plugin library is a
substitute for a process boundary.

The current root configuration options that control this surface are:
\begin{itemize}
\item \texttt{GENESYS\_BUILD\_TERMINAL\_APPLICATION};
\item \texttt{GENESYS\_BUILD\_WORKER\_APPLICATION};
\item \texttt{GENESYS\_BUILD\_GUI\_APPLICATION};
\item \texttt{GENESYS\_BUILD\_TERMINAL\_EXAMPLES};
\item \texttt{GENESYS\_BUILD\_TOOLS}.
\end{itemize}

The GUI umbrella adds its own switches for the main GUI, the HTTP Worker GUI,
the Data Analyser, the Optimizer, the AI Assistant, and the guarded
\texttt{GENESYS\_BUILD\_GUI\_DOEXPERIMENTS} placeholder. That layering keeps
the process map explicit while still allowing partial builds.

The current static plugins remain part of the simulator backbone, not separate
processes. Likewise, \texttt{genesys\_tools} is a library and
\texttt{genesys\_tools\_application} is the optional support process built on
top of it. The same distinction applies to \texttt{genesys\_worker\_core}
versus \texttt{genesys\_worker\_app}.

\section{Startup, shutdown, and errors}
\label{sec:application-architecture-runtime-flow}

The startup and shutdown mechanics differ slightly by executable family, but
the architectural pattern is the same: the composition root builds the runtime,
the runtime enters its main loop, and the process returns an exit code when the
loop ends or a startup error occurs.

The shell and model-specific routes use RAII around a selected application
object and then return the selected application's exit code. The tools CLI
either prints its inventory or reports an unknown command to standard error.

The worker logs that it is listening, then calls \texttt{serve()} on its
embedded HTTP server. If the server cannot start or bind, the worker prints a
startup failure and returns a non-zero exit code. The server loop and request
limit control the normal stop path.

The main GUI installs crash and logging handlers before \texttt{QApplication}
is created. It then loads preferences, applies the theme, builds the main
window, and enters the Qt event loop. Shutdown occurs when the event loop
returns or a fatal crash handler aborts the process.

The standalone Qt frontends follow the same broad pattern: each process owns
its own Qt application object, window, and exit code. Their error handling is
local to the process and should not be interpreted as a cross-process recovery
mechanism.
