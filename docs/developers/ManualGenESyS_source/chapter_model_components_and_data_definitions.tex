\chapter{Model Components and Data Definitions}
\label{chap:model-components-and-data-definitions}

This chapter explains the shared data-definition layer used by the current
kernel, the component specialization built on top of it, and the registry and
ownership rules that keep the model consistent. In the current code base, the
distinction between a "component" and a "model data definition" is not a
separate storage model. It is a behavioral split built on a common base class.

\noindent\textbf{Objective.} Describe how model components and model data
definitions are represented, managed, created, connected, validated, and
persisted in the current branch.

\noindent\textbf{Audience.} Developers who extend the simulation kernel or add
new component and data-definition types.

\noindent\textbf{Scope.} Cover the shared base class, the component subclass,
the managers, the internal/attached data lifecycle, the persistence round-trip,
and a concrete example of the current behavior.

\noindent\textbf{Status.} Confirmed by code inspection on 2026-07-23 and by
the lifecycle tests that exercise \texttt{Station}, \texttt{Queue}, \texttt{Resource}, and the core
model-data destructor paths.

\section{Shared vocabulary}
\label{sec:model-component-shared-vocabulary}

The current kernel uses \texttt{ModelDataDefinition} as the shared base for most
runtime model objects that need identity, persistence, trace integration, and
model-managed lifetime. Concrete examples in the repository include
\texttt{Queue}, \texttt{Resource}, \texttt{Variable}, \texttt{Station}, \texttt{Attribute}, and many plugin
specific definitions.

\texttt{ModelComponent} is a specialization of \texttt{ModelDataDefinition}. It adds the
outgoing connection manager and the event-dispatch hook used by the future
event list. That means components are not a separate class family outside the
model-data layer; they are the event-driven subset of it.

The managers keep those responsibilities separated:
\begin{itemize}
\item \texttt{ModelDataManager} stores all registered \texttt{ModelDataDefinition} instances
      grouped by runtime typename;
\item \texttt{ModelComponentManager} stores only \texttt{ModelComponent} instances and
      preserves a component-oriented iteration order;
\item \texttt{ModelDataDefinitionAssociations} maintains the internal and attached
      child registries that belong to one definition instance.
\end{itemize}

\section{How the model owns the objects}
\label{sec:model-component-ownership}

\texttt{ModelDataDefinition} constructs an instance with a generated id, a runtime
typename, a stable name, and a back-reference to the parent \texttt{Model}. When the
constructor is told to register immediately, it inserts the instance into the
model's data manager. It also creates the standard control set for \texttt{Name},
\texttt{Label}, \texttt{Report Statistics}, and \texttt{Trace Level}, then registers those controls
with the model.

The destructor reverses that work conservatively. It clears the internal and
attached association buckets, removes the instance from the model data manager,
and then removes and deletes any owned \texttt{SimulationControl} or
\texttt{SimulationResponse} objects. The code paths exercised by
\texttt{SimulatorRuntimeTest} confirm that owned internal data is deleted, attached
data is not deleted, and owned controls are removed from the model registry.

\texttt{ModelComponent} adds one more layer on top. Its constructor calls the base
constructor with deferred insertion, then registers the new component in the
component manager and creates a dedicated \texttt{ConnectionManager}. Its destructor
removes the component from the component manager before deleting the connection
manager. The connection manager stores outgoing links together with the target
input port number.

The ownership boundary is therefore explicit:
\begin{itemize}
\item a raw pointer to a model data definition does not imply ownership by
      itself;
\item internal data is owned by the parent definition when inserted through
      the association helpers;
\item attached data is a non-owning relationship used as a reference;
\item component connections are owned by the source component's connection
      manager, not by the target component;
\item \texttt{ModelDataManager} and \texttt{ModelComponentManager} are registries, not the
      lifetime owners of external objects by pointer syntax alone.
\end{itemize}

\section{Creation and validation}
\label{sec:model-component-creation-and-validation}

The model layer creates definitions and components through a combination of
constructors, plugin factories, and template helper methods:
\begin{itemize}
\item the constructors establish identity and insert the instance into the
      correct manager;
\item \texttt{ModelDataDefinition::CreateInternalData} materializes the
      internal helper objects needed by a definition;
\item \texttt{ModelComponent::CreateInternalData} does the same for
      components;
\item the \texttt{\_templateCreate...} wrappers call the overridable hooks and convert
      exceptions into trace output instead of leaving the model in an
      unreported partial state;
\item \texttt{ModelDataDefinition::Check} and \texttt{ModelComponent::Check} drive
      object-specific validation;
\item \texttt{ModelDataDefinition::InitBetweenReplications} resets internal children
      between replications.
\end{itemize}

The association layer is the part that turns those hooks into concrete data.
\texttt{ModelDataDefinitionAssociations} keeps the legacy \texttt{internalData}
and \texttt{attachedData} maps alive. It also provides narrower buckets for
statistic reporters, mandatory attached attributes, and editable versus
non-editable data definitions. That compatibility layer matters because the
current tree still uses the older direct map accessors in several places.

Concrete subclasses use those hooks in different ways:
\begin{itemize}
\item \texttt{Station} lazily creates internal \texttt{StatisticsCollector} objects when
      report statistics are enabled;
\item \texttt{Queue} and \texttt{Resource} lazily create their accounting collectors on the
      first operation that needs them;
\item \texttt{Variable} keeps a runtime value store synchronized with its initial
      values and exposes a \texttt{Scope} control;
\item some biochemical and whole-cell definitions use the editable-data hook
      to materialize model-specific helper objects.
\end{itemize}

\section{Persistence round-trip}
\label{sec:model-component-persistence}

Persistence uses the same split between base data and component behavior.
\texttt{ModelDataDefinition::SaveInstance} writes the shared metadata fields.
\texttt{ModelComponent::SaveInstance} adds the component-specific connection
fields. On load, \texttt{ModelDataDefinition::\_loadInstance} restores the core
metadata, and \texttt{ModelComponent::\_loadInstance} restores the free-form
description and the component-specific fields.

The important detail is that connections are not restored as a fully linked
graph in one pass. The serializer writes \texttt{nextId} and \texttt{nextinputPortNumber}
fields, but loading still needs the target components to exist before those
links can be reconnected. That is why the chapter treats persistence as a
two-step round-trip: first the definitions are instantiated, then the topology
is reattached.

The same distinction applies to data definitions that own internal children.
Their internal objects are serialized through the owning object's own save
logic, not through a generic graph dumper. The current format is therefore a
managed object graph, not a free-standing abstract tree.

\section{Concrete example}
\label{sec:model-component-concrete-example}

The current branch contains several concrete examples of the shared pattern.
\texttt{Station} is the clearest data-definition example because it creates and reuses
internal statistics collectors only when report statistics are enabled. The
lifecycle tests show that the first \texttt{enter()} call materializes
\texttt{NumberInStation} and \texttt{TimeInStation}, repeated calls reuse the same objects,
and disabling report statistics suppresses the collectors entirely.

\texttt{Queue} and \texttt{Resource} show the same lazy-materialization pattern for their
accounting collectors. Their tests confirm that the internal definitions are
created on first use, reused on later operations, and absent when report
statistics are disabled.

\texttt{Variable} demonstrates a different specialization. It still uses the same
shared base, but its runtime behavior is centered on the value store and the
\texttt{Scope} control rather than on statistics collectors.

Taken together, those examples show the current design intent:
\begin{itemize}
\item the base class handles identity, trace integration, controls, and
      persistence metadata;
\item the association layer handles owned versus referenced helper data;
\item concrete subclasses choose which helper objects to materialize and when;
\item the managers keep the registry state synchronized with the lifetime of
      the objects themselves.
\end{itemize}
