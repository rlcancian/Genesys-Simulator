\chapter{Worker and Remote Execution}
\label{chap:worker-and-remote-execution}

This chapter documents the current Worker architecture as it exists in the active branch on 2026-07-23. It is based on the standalone worker sources, the reusable embedded worker runtime, the root repository guidance, and the current worker application README. The chapter describes the current snapshot, not a future idealized distributed platform.

\noindent\textbf{Objective.} Explain how the Worker process is composed, how requests move through transport, routing, sessions, and job handling, and where the current security and deployment boundary stops.

\noindent\textbf{Audience.} Developers and maintainers who need a faithful map of the Worker before changing HTTP routes, session behavior, job handling, deployment assumptions, or embedded-runtime integration.

\noindent\textbf{Scope.} Cover the standalone \texttt{genesys-worker} executable, the reusable \texttt{WebWorkerRuntime} wrapper, the HTTP transport layer, token and session management, the current API surface, worker jobs, logging, and the local/private deployment boundary.

\noindent\textbf{Status.} Confirmed by repository inspection on 2026-07-23. The chapter is conservative about maturity: the Worker exposes discovery and job-oriented endpoints, but it does not provide TLS, quotas, public-Internet approval, or background distributed execution.

\section{Worker process boundary}
\label{sec:worker-architecture-process-boundary}

The current Worker is not a GUI widget and not a kernel subsystem. It is an executable application that owns its own entry point, its own HTTP stack, and its own session registry. The standalone target is \texttt{genesys\_worker\_app}, which produces the executable name \texttt{genesys-worker}; the build also keeps the alias target \texttt{genesys\_worker}.

The standalone entry point in \texttt{BaseGenesysWebApplication} wires together
these objects:
\begin{itemize}
\item \texttt{TokenService};
\item \texttt{SessionManager};
\item \texttt{WorkerJobManager};
\item \texttt{SimulatorSessionService};
\item \texttt{ApiRouter};
\item \texttt{SimpleHttpServer}.
\end{itemize}
The command-line wrapper accepts \texttt{--port} and \texttt{--max-requests}.
The port defaults to 8080 and the request cap defaults to unlimited.

The same stack is also reused by \texttt{WebWorkerRuntime}, which is the embedded lifecycle wrapper used by GUI-facing code. That wrapper keeps the worker stack behind a start/stop/restart interface and exposes a bounded snapshot of runtime state, recent events, and recent errors. The important architectural point is that the embedded runtime reuses the same worker core instead of reimplementing the HTTP and session logic in the GUI.

\section{HTTP transport and request routing}
\label{sec:worker-architecture-transport}

The HTTP transport is intentionally small. \texttt{SimpleHttpServer} is a blocking, one-request-per-connection server that accepts a connection, reads one bounded HTTP/1.1 request, delegates to the route handler, serializes the response, and closes the socket. It does not implement keep-alive or chunked transfer decoding.

The transport layer enforces a 1 MiB request cap and 5 second socket read/write timeouts. It maps transport failures to standard JSON responses: invalid requests become 400, timeouts become 408, oversized requests become 413, and unexpected server errors become 500. The server binds to \texttt{INADDR\_ANY} on the configured port.

\texttt{ApiRouter} keeps the route logic separate from transport. It resolves public discovery routes, session routes, simulation routes, and worker-job routes, then returns a compact JSON response model with stable error codes. The router is explicit on purpose: the current source tree is easier to audit when the public routes are spelled out in one place.

\section{Session, token, and workspace model}
\label{sec:worker-architecture-session-model}

Authenticated worker sessions are owned by \texttt{SessionManager}. Each session binds one bearer token to one simulator instance, one session identifier, and one filesystem workspace rooted under the system temporary directory. The current root is \texttt{temp\_directory\_path()/genesys\_worker\_sessions}.

\texttt{TokenService} generates two opaque identifiers: a session id with the \texttt{sess\_} prefix and a bearer token encoded as hex. The session manager stores sessions in a token-to-session map, and each created session receives a fresh \texttt{Simulator} instance from the provided factory. The simulator is then initialized with the default plugin set so that language import and snapshot loading can resolve built-in model elements immediately.

The workspace boundary matters. Persistence operations are limited to the session workspace directory, and filename inputs are treated as safe basenames only. The current rules reject absolute paths, parent-path traversal, slashes, backslashes, and names that do not match the safe filename pattern. That keeps the Worker from acting as a general file server.

\section{Current API surface}
\label{sec:worker-architecture-api-surface}

The public and authenticated routes are split into discovery, session, simulation, and worker-job groups.

The discovery surface currently includes:
\begin{itemize}
\item \texttt{GET /health};
\item \texttt{POST /api/v1/auth/session};
\item \texttt{GET /api/v1/worker/info};
\item \texttt{GET /api/v1/worker/capabilities}.
\end{itemize}

The session-scoped surface currently includes:
\begin{itemize}
\item \texttt{GET /api/v1/simulator/info};
\item \texttt{POST /api/v1/models};
\item \texttt{GET /api/v1/models/current};
\item \texttt{POST /api/v1/models/save};
\item \texttt{POST /api/v1/models/load};
\item \texttt{GET /api/v1/simulation/status};
\item \texttt{POST /api/v1/simulation/config};
\item \texttt{POST /api/v1/simulation/run};
\item \texttt{POST /api/v1/simulation/step};
\item \texttt{POST /api/v1/worker/models/import-language};
\item \texttt{POST /api/v1/worker/jobs};
\item \texttt{GET /api/v1/worker/jobs/\{jobId\}};
\item \texttt{POST /api/v1/worker/jobs/\{jobId\}/run};
\item \texttt{GET /api/v1/worker/jobs/\{jobId\}/result}.
\end{itemize}

The discovery endpoints do not require a bearer token. The remaining routes do. The capability payload intentionally exposes the current implementation boundary: session API support is present, synchronous run and step are present, model upload through plain text import is present, background execution is false, and streaming events are false. The job-oriented flags currently describe the current API surface, not a background distributed executor.

\section{Worker jobs and synchronous execution}
\label{sec:worker-architecture-jobs}

Worker jobs are stored in memory by \texttt{WorkerJobManager}. A newly created job receives a monotonic identifier of the form \texttt{job-<n>} and a creation marker of the form \texttt{seq-<n>}. The creation marker preserves ordering, while the job id is the public handle exposed by the API.

Job creation requires a current model in the session. The implementation then writes a snapshot file named \texttt{job\_<id>.gen} into the session workspace so that later execution can be decoupled from live model mutations. That snapshot is the execution source for the \texttt{/run} path.

Execution is synchronous. The current run path loads the stored snapshot back into the session simulator, calls \texttt{simulation->start()}, and records a minimal terminal summary with simulated time, replication numbers, replication length, warm-up period, and optional paused state. If execution fails, the job is marked failed and the terminal summary is still preserved when possible.

The query path and result path remain session-scoped. A job that belongs to another session is treated as inaccessible, and a terminal result is not returned until the job has reached a finished or failed state with stored terminal data.

\section{Security, logging, and recovery boundary}
\label{sec:worker-architecture-security}

The current Worker boundary is local or private network only. The standalone server binds to all interfaces on the selected port, but the repository guidance does not approve direct public-Internet exposure. The current code does not implement TLS, credential rotation, quotas, per-request authorization beyond the opaque bearer token, or service-level isolation controls. Those are future hardening items, not current guarantees.

The transport and API layers do provide basic failure handling. Invalid HTTP requests become 400 responses; expired or malformed session tokens become 401 responses; missing current models become 409 responses; missing or invalid worker jobs become 404 or 409 depending on the failure mode; transport overload becomes 413; and unexpected exceptions become 500. That behavior is useful for debugging, but it is not a security story by itself.

\texttt{WebWorkerRuntime} keeps recent events and recent errors in bounded in-memory deques, together with a thread-safe snapshot of the worker state. That gives the GUI or other callers a lightweight way to observe whether the background worker is starting, running, stopping, or failed. It does not make job state persistent across process restarts, and it does not replace external monitoring or audit logging.

\section{Practical reading order}
\label{sec:worker-architecture-reading-order}

For maintainers, the most useful reading order is:
\begin{enumerate}
\item \texttt{BaseGenesysWebApplication} for the standalone process boundary;
\item \texttt{SimpleHttpServer} for transport limits and response mapping;
\item \texttt{ApiRouter} for the route table and public wire contract;
\item \texttt{TokenService}, \texttt{SessionManager}, and
      \texttt{SessionContext} for authentication scope and workspace isolation;
\item \texttt{SimulatorSessionService} for model, simulation, and job behavior;
\item \texttt{WorkerJobManager} for job storage and terminal result handling;
\item \texttt{WebWorkerRuntime} for the embedded lifecycle wrapper.
\end{enumerate}

As illustrated by Figures~\ref{fig:worker-architecture-runtime-map},
\ref{fig:worker-architecture-request-flow},
\ref{fig:worker-architecture-session-flow},
\ref{fig:worker-architecture-api-surface},
\ref{fig:worker-architecture-job-lifecycle}, and
\ref{fig:worker-architecture-security-boundary},
the current Worker is already a coherent application boundary, but it is still intentionally conservative in security, transport, and execution model.
